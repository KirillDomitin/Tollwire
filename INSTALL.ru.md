# Установка и запуск

[English](INSTALL.md) · Русский

Tollwire — панель управления VPN-серверами. Это четыре части:

| Часть | Что делает | Как запускается |
|---|---|---|
| **API** | REST API на FastAPI | `uvicorn` |
| **Воркер** | фоновые задачи (установка, выдача конфигов, проверки) и планировщик | `python src/worker.py` |
| **Фронтенд** | админ-панель (React + Vite) | dev-сервер Vite / статика в nginx |
| **PostgreSQL + Redis** | данные; очередь задач и блокировки | Docker |

Без воркера панель открывается, но задачи (установка, выдача и отзыв конфигов, проверки) стоят в очереди и не выполняются.

- [Разработка (dev)](#разработка-dev)
- [Продакшен (prod)](#продакшен-prod)
- [Частые проблемы](#частые-проблемы)

## Разработка (dev)

Локально: PostgreSQL и Redis — в Docker, API, воркер и фронтенд — прямо на машине.

### Что нужно установить

| Инструмент | Версия | Зачем |
|---|---|---|
| Docker + Docker Compose | любая свежая | PostgreSQL и Redis |
| Python | 3.12+ (в образе — 3.14) | бэкенд |
| [uv](https://docs.astral.sh/uv/) | свежая | зависимости Python (строго по `uv.lock`) |
| Node.js | 24 | фронтенд |

Команды ниже — для bash (Linux, macOS, Git Bash на Windows). Отличия для PowerShell — в конце раздела.

### 1. Зависимости

```bash
git clone <адрес репозитория> tollwire
cd tollwire
uv sync
cd frontend && npm ci && cd ..
```

### 2. PostgreSQL и Redis

```bash
docker compose up -d
```

Поднимает `postgres` (пользователь `user`, пароль `password`, база `vpn_panel`) и `redis`. Оба слушают **только localhost** (`127.0.0.1:5432`, `127.0.0.1:6379`) — пароли тут учебные, наружу их не открываем.

### 3. Файл `.env`

```bash
cp .env.example .env
```

В `.env` обязательно заменить два значения (с заглушками приложение не запустится или будет небезопасно):

```bash
# JWT_SECRET_KEY — не короче 32 символов и не «change_me…» (иначе API не стартует)
uv run python -c "import secrets; print(secrets.token_hex(32))"

# ENCRYPTION_KEY — ключ Fernet, им шифруются SSH-учётки и VPN-конфиги в БД
uv run python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
```

Остальное в `.env.example` уже настроено под dev (`DATABASE_URL`, `REDIS_URL`, `COOKIE_SECURE=false` — локально API работает по http).

> `ENCRYPTION_KEY` нельзя менять после того, как в базу записали SSH-учётки или конфиги: старые записи станут нечитаемыми.

### 4. Миграции

```bash
uv run alembic upgrade head
```

### 5. Первый админ

```bash
PYTHONPATH=src uv run python -m scripts.create_admin
```

Скрипт спросит email и предложит пароль: **случайный** (по умолчанию — показывается один раз, нигде не сохраняется, при первом входе панель попросит задать свой) или свой (вводится скрыто, не короче 12 символов). `--random-password` пропускает вопросы; `--only-if-empty` ничего не делает, если админы уже есть. Роль по умолчанию — `superadmin`; для других ролей — `--role operator` или `--role viewer` (их удобнее заводить в самой панели).

Запускать из корня репозитория и **в интерактивном терминале**. Случайный пароль показывается только в терминале: при выводе в файл или через конвейер (`| tee`) скрипт откажется, чтобы пароль не остался в логе.

### 6. Запуск

Три процесса, каждый в своём терминале:

```bash
# API → http://localhost:8000
uv run uvicorn main:app --app-dir src --reload --port 8000
```

```bash
# Воркер (задачи + планировщик)
uv run python src/worker.py
```

```bash
# Фронтенд → http://localhost:5173
cd frontend && npm run dev
```

Панель — **http://localhost:5173**. Vite проксирует `/api` на `localhost:8000`, поэтому для браузера фронтенд и API — один адрес (как в проде): refresh-cookie работает, CORS не нужен.

Документация API (Swagger) — http://localhost:8000/api/openapi, проверка живости — http://localhost:8000/health.

> **Воркер подключается к настоящим серверам.** Его планировщик периодически запускает проверку состояния (health) и сверку (sync) всех серверов из базы. Если в dev-базе есть боевые серверы — помните об этом, или выключите планировщик: `SCHEDULER_ENABLED=false` в `.env`.

### Проверки перед коммитом

```bash
# бэкенд
uv run ruff check . && uv run ruff format --check .
uv run mypy src
uv run pytest          # нужен docker compose up: тесты создают свою БД vpn_panel_test и берут Redis db 15

# фронтенд
cd frontend
npm run typecheck && npm run lint && npm test && npm run build
```

### Изменили API — обновите типы фронтенда

Фронтенд берёт типы запросов и ответов из OpenAPI-схемы бэкенда. После изменения схем или эндпоинтов:

```bash
PYTHONPATH=src uv run python -m scripts.export_openapi frontend/openapi.json
cd frontend && npm run gen:api
```

Сервер для этого запускать не нужно — схема выгружается из кода.

### PowerShell (Windows)

Отличается только установка переменной окружения:

```powershell
$env:PYTHONPATH = "src"; uv run python -m scripts.create_admin you@example.com
$env:PYTHONPATH = "src"; uv run python -m scripts.export_openapi frontend/openapi.json
```

## Продакшен (prod)

Всё в Docker (`docker-compose.prod.yml`):

```
интернет ── 80/443 ──► nginx ──► api ──► postgres, redis
                    (статика      worker ──► postgres, redis
                     фронтенда)           └─► SSH к VPN-серверам
```

- наружу открыт **только nginx** (80 → редирект на 443, HTTPS);
- `api`, `worker` и одноразовый `migrate` — один образ из корневого `Dockerfile`;
- `postgres` и `redis` — во внутренней сети без выхода в интернет;
- миграции применяются автоматически при каждом запуске (`migrate`), api и воркер стартуют только после них;
- документация API (`/api/openapi`) в проде выключена.

### Быстрая установка

```bash
git clone <адрес репозитория> tollwire && cd tollwire
./install.sh --domain panel.example.com
```

За один запуск установщик проверит Docker, создаст `.env.prod` со случайными секретами, выпустит TLS-сертификат, запустит панель, дождётся её готовности и предложит создать первого администратора (случайный пароль показывается один раз, при первом входе панель потребует задать свой). Первая сборка образов занимает несколько минут. Повторный запуск безопасен: существующие `.env.prod` и сертификат не затрагиваются, панель просто приводится к рабочему виду. Шаги ниже описывают то же самое вручную.

Параметры: `--domain`, `--cert`/`--key` (свой сертификат), `--admin-email`, `--bot local|remote|none` (Telegram-бот, см. ниже), `--no-start` (только подготовить файлы). `INSTALL_WAIT_SECONDS` — сколько ждать готовности (по умолчанию 300 с); порты `HTTP_PORT`/`HTTPS_PORT` берутся из окружения или `.env.prod`. Сообщения на английском или русском: `PANEL_LANG=ru|en`, иначе по локали системы.

### Если сервер не может скачать образы

В некоторых сетях соединения к CDN Docker и npm обрываются после нескольких килобайт (загрузка зависает с `connection timed out`). Тогда соберите образы на компьютере с нормальным интернетом и отправьте по SSH:

```bash
# на этом компьютере, из корня репозитория (нужен вход на сервер по SSH-ключу)
./deploy/ship-images.sh мой-сервер        # имя из ~/.ssh/config или user@host
```

Скрипт соберёт `vpn-panel` и `vpn-panel-web` из закоммиченного состояния (git HEAD), передаст их на сервер и пометит там нужными именами. `postgres` и `redis` сервер тянет сам по закреплённым дайджестам; если и это зависает, привезите их так же (`docker save | gzip | ssh ... 'gunzip | docker load'`) и укажите имена в `.env.prod`: `POSTGRES_IMAGE=...`, `REDIS_IMAGE=...`. На сервере запускайте без сборки:

```bash
./install.sh --domain panel.example.com --no-build       # первая установка
./panel update --no-pull --no-build                      # потом: снова привезти образы, затем это
```

### Что нужно

- Linux-сервер с Docker и **Docker Compose 2.24 или новее** (плагин `docker compose`): compose-файл панели использует `env_file` с `required`, на старых версиях падает любая команда;
- домен, указывающий на сервер, и TLS-сертификат для него;
- открытые входящие порты 80 и 443; исходящий доступ по SSH к VPN-серверам (его использует воркер).

### 1. Код

```bash
git clone <адрес репозитория> vpn-panel
cd vpn-panel
```

### 2. Секреты: `.env.prod`

**Автоматически** (`./install.sh` делает это первым): проверяет Docker, Compose и openssl и создаёт `.env.prod` со случайными паролем БД, JWT-секретом и ключом шифрования (права 600, на экран секреты не выводятся). Без `--domain` в терминале спросит адрес панели. Существующий `.env.prod` не трогается никогда; если файла нет, но на сервере остался том базы от прошлой установки (`vpn-panel_pg_data`), установщик остановится: новые секреты к этой базе не подойдут.

**Вручную:**

```bash
cp .env.prod.example .env.prod
chmod 600 .env.prod
```

Заполнить:

| Переменная | Чем заполнить |
|---|---|
| `POSTGRES_PASSWORD` | `openssl rand -hex 32` — только `[0-9a-f]`, пароль подставляется в URL базы |
| `JWT_SECRET_KEY` | `openssl rand -hex 32` |
| `ENCRYPTION_KEY` | ключ Fernet — см. ниже |

Ключ Fernet, если на сервере нет Python с `cryptography`, — через собранный образ приложения:

```bash
docker compose --env-file .env.prod -f docker-compose.prod.yml build api
docker run --rm vpn-panel:latest python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
```

`DATABASE_URL`, `REDIS_URL`, `COOKIE_SECURE`, `LOG_FORMAT` в `.env.prod` не задаются — их собирает `docker-compose.prod.yml`.

> **`ENCRYPTION_KEY` — самое ценное.** Им зашифрованы SSH-учётки серверов и VPN-конфиги в базе. Потеряете — бэкап базы бесполезен; смените — старые записи не расшифровать. Храните копию отдельно от сервера (менеджер паролей, сейф). `.env.prod` и `certs/` — в `.gitignore`, в git они не попадают.

### 3. TLS-сертификат

**Автоматически** (`./install.sh` делает это сразу после `.env.prod`):

- в терминале спрашивает, какой сертификат нужен: **самоподписанный** (по умолчанию, для пробы: 825 дней, браузер предупредит, что ему не доверяет; отпечаток SHA-256 установщик покажет — сверьте с браузером), **Let's Encrypt** или свои файлы;
- **Let's Encrypt** (`./install.sh --domain panel.example.com --letsencrypt` или пункт 2 в меню): настоящий сертификат, без предупреждений браузера. Нужны настоящее доменное имя, которое указывает на этот сервер, и порт 80, доступный из интернета. Установщик сам поставит `certbot`, если его нет (apt или dnf, нужен sudo), на несколько секунд остановит nginx панели, пока certbot проверяет домен, и положит сертификат в `certs/`. [Условия Let's Encrypt](https://letsencrypt.org/repository/) принимаете вы сами: ответом в меню или флагом `--accept-le-terms`, если терминала нет (`--le-email` добавляет адрес для уведомлений об истечении). Сертификат обновляется сам: системный таймер certbot раз в сутки проверяет срок и при необходимости на несколько секунд останавливает nginx и подменяет файлы. Если выпуск не удался (например, провайдер блокирует входящие соединения или роутер не пробрасывает порт 80), панель всё равно запустится с самоподписанным сертификатом, а установщик подскажет, как повторить;
- уже установленная панель: `./panel cert` показывает издателя и срок, `./panel cert letsencrypt` переходит на Let's Encrypt, `./panel cert renew` проверяет обновление;
- свой сертификат: `./install.sh --cert fullchain.pem --key privkey.pem` — файлы проверяются (PEM, ключ подходит к сертификату, срок не вышел) и копируются в `certs/`. Можно и просто положить их в `certs/` и запустить установщик снова;
- существующие файлы в `certs/` **никогда не заменяются**: установщик только проверяет пару и предупреждает, если сертификат скоро истекает или не покрывает адрес. Чтобы заменить сертификат, удалите оба файла осознанно.

**Вручную.** nginx ждёт два файла:

```
certs/fullchain.pem   — сертификат с цепочкой
certs/privkey.pem     — приватный ключ
```

Например, из Let's Encrypt: получить сертификат (certbot) и скопировать `fullchain.pem` и `privkey.pem` в `certs/`. После обновления сертификата — `docker compose --env-file .env.prod -f docker-compose.prod.yml restart nginx`.

Для пробного запуска без домена подойдёт самоподписанный сертификат (браузер предупредит):

```bash
mkdir -p certs
openssl req -x509 -newkey rsa:2048 -nodes -days 30 -subj "/CN=localhost" \
  -keyout certs/privkey.pem -out certs/fullchain.pem
```

### 4. Запуск

`./install.sh` делает это сам: проверяет, что порты 80/443 свободны, выполняет `up -d --build` и ждёт, пока контейнер `api` станет здоровым, а nginx ответит на `/health` по HTTPS. Вручную:

```bash
docker compose --env-file .env.prod -f docker-compose.prod.yml up -d --build
```

`--env-file .env.prod` обязателен: из него берутся пароль базы и порты для самого compose-файла.

Проверка:

```bash
docker compose --env-file .env.prod -f docker-compose.prod.yml ps   # migrate — exited (0), остальные — running/healthy
curl -fsS https://<ваш-домен>/health
```

### 5. Первый админ

```bash
docker compose --env-file .env.prod -f docker-compose.prod.yml run --rm api python -m scripts.create_admin
```

Спросит email и пароль: **случайный** (по умолчанию — показывается один раз, нигде не сохраняется; при первом входе панель потребует задать свой) или свой (не короче 12 символов). `--only-if-empty` ничего не делает, если админы уже есть. `./install.sh` выполняет этот шаг сам, когда есть терминал; без терминала печатает готовую команду. Дальше — вход на `https://<ваш-домен>`, остальных админов удобнее заводить в панели.

### Telegram-бот (необязательно)

Человек получает доступ по пригласительной ссылке: открывает бота по ссылке, называет имя и почту и подтверждает. Панель регистрирует его, бот сообщает, что доступ готов; конфиг присылает администратор (ссылки на конфиг в боте пока нет). Бот — отдельный контейнер. Он ходит в панель только через Bot API со своим ключом и секретов панели не получает.

**1. Создайте бота.** Напишите [@BotFather](https://t.me/BotFather), отправьте `/newbot` и сохраните токен (`123456789:AAF…`). Токен никогда не пишется в `.env.prod`.

**2. Выберите, где он будет работать.**

**На сервере панели:** `./install.sh --bot local` или ответ `1` на вопрос в терминале при первой установке (по умолчанию `3` — без бота). Установщик спрашивает токен скрытым вводом (или берёт `TELEGRAM_BOT_TOKEN` из окружения), проверяет его у Telegram, выпускает ключ, записывает `.env.bot` (только для владельца) и запускает контейнер `bot`. С этого сервера должен открываться `api.telegram.org` по исходящему порту 443. Если не открывается, запустите бота на другом сервере.

**На другом сервере** (например, когда Telegram заблокирован там, где стоит панель): `./install.sh --bot remote` или позже `./panel bot key --remote`. Панель выпускает ключ и печатает команду для второго сервера:

```bash
git clone <адрес-репозитория> tollwire && cd tollwire
./bot/install-bot.sh --panel-url https://panel.example.com --panel-fingerprint <SHA-256>
```

На втором сервере (нужны Docker и git; исходящий порт 443 до `api.telegram.org` и до панели) скрипт спрашивает ключ и токен скрытым вводом или берёт `BOT_API_KEY` и `TELEGRAM_BOT_TOKEN`. Ключ показывается один раз, только в терминале, и в команду не попадает. Адрес панели — `https://`.

`--panel-fingerprint` печатается только для самоподписанного сертификата панели. Сверьте его с SHA-256 из `./panel cert status` на сервере панели. Без отпечатка скрипт в терминале спросит подтверждение, без терминала откажется. Для сертификата Let's Encrypt отпечаток не нужен.

**3. Управление** (на сервере панели):

| Команда | Что делает |
|---|---|
| `./panel bot enable` | включить бота здесь (если бот ещё не настроен, спросит токен); `--no-build` берёт образ, привезённый `ship-images.sh` |
| `./panel bot disable` | остановить бота и убрать из запуска; его настройки сохраняются, ключ остаётся действующим |
| `./panel bot key` | заменить ключ: новый записывается, бот перезапускается; старый ключ отзывается только после того, как бот вышел на связь с новым |
| `./panel bot key --remote` | выпустить ключ для бота на другом сервере и показать его один раз |
| `./panel bot revoke` | отозвать ключ (вставить в скрытый запрос) |
| `./panel bot status` | ключи и когда бот был на связи |
| `./panel bot invite protocols` | протоколы, на которые можно пригласить, с их id |
| `./panel bot invite create --protocol ID --days 30 --expires-in 7d` | создать одноразовое приглашение на 30 дней доступа; `--expires-in` — `7d` или `12h`; `--note ТЕКСТ` — кому |

`invite create` печатает ссылку `t.me/<бот>?start=<код>`, один раз. Для ссылки нужно имя бота, его бот сообщает панели при первом выходе на связь; до этого печатается только код.

Установщик добавляет в `.env.prod` строку `COMPOSE_PROFILES=bot`: бот входит в compose-проект панели (`down` останавливает и его); `./panel bot disable` убирает `bot` из этой строки. Логи: `./panel logs bot`; бот на другом сервере — `docker compose -f bot/docker-compose.yml logs bot` на нём.

`./deploy/ship-images.sh SERVER` вместе с панелью отправляет и образ бота `vpn-panel-bot:latest`, если в репозитории есть `bot/`. С `--no-build` установщик проверяет, что этот образ есть на машине, когда бот включён. Бот на другом сервере собирается там.

`./panel update` про бота не спрашивает и его настройки не меняет.

### Обновление

```bash
./panel update
```

Делает бэкап базы, `git pull --ff-only`, пересобирает и запускает панель (та же логика, что в `./install.sh`, поэтому дожидается готовности). Если папка — не git-репозиторий или в отслеживаемых файлах есть локальные правки, остановится, ничего не сделав: обновите код сами и используйте `--no-pull`; `--no-backup` пропускает бэкап. Если запуск не удался, сообщение назовёт бэкап и путь назад (`./panel restore`). Вручную:

```bash
git pull
docker compose --env-file .env.prod -f docker-compose.prod.yml up -d --build
```

Новые миграции применятся сами (сервис `migrate`). Воркер при остановке дожидается текущей задачи (до 60 с).

### Логи

Логи — в JSON, по строке на событие; запрос в nginx и его обработку в api связывает общий `request_id`:

```bash
./panel logs api worker                  # последние 100 строк и слежение; --tail N, --no-follow
docker compose --env-file .env.prod -f docker-compose.prod.yml logs --no-log-prefix api | jq .
```

Пароли, ключи, токены и VPN-конфиги в логи не пишутся. `LOG_LEVEL=debug` в `.env.prod` добавляет текст каждой SSH-команды (без её вывода).

### Резервная копия

```bash
./panel backup                           # backups/tollwire-ГГГГММДД-ЧЧММСС.dump (права 600), хранятся последние 14
./panel backup --keep 30 --dir /mnt/backups
./panel restore backups/tollwire-20261016-030000.dump
```

`backup` снимает дамп базы в формате `pg_dump -Fc`, проверяет файл и только потом кладёт его на место; старые бэкапы сверх `--keep` удаляются (страховочные копии и чужие файлы в папке не трогаются). Безопасно запускать из cron:

```
0 3 * * * cd /opt/tollwire && ./panel backup >> /var/log/tollwire-backup.log 2>&1
```

`restore` **заменяет** все данные панели дампом. Просит ввести `restore` (без терминала нужен `--yes`), сначала делает страховочный бэкап текущих данных (`tollwire-pre-restore-….dump`; `--no-safety-backup` отключает), останавливает `api` и `worker`, загружает дамп одной транзакцией (при ошибке база остаётся как была, сервисы запускаются снова), применяет миграции на случай, если дамп старше кода, и запускает панель.

**`.env.prod` в бэкап не входит — так задумано.** Дамп без `ENCRYPTION_KEY` из вашего `.env.prod` бесполезен; и наоборот, тот, кто унесёт только дамп, не прочитает SSH-учётки и VPN-конфиги в нём. Храните копию `.env.prod` в менеджере паролей или сейфе — отдельно от этого сервера и от бэкапов.

Вручную:

```bash
docker compose --env-file .env.prod -f docker-compose.prod.yml exec -T postgres \
  sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' > backup-$(date +%F).dump
docker compose --env-file .env.prod -f docker-compose.prod.yml exec -T postgres \
  sh -c 'pg_restore -U "$POSTGRES_USER" -d "$POSTGRES_DB" --clean --if-exists' < backup-YYYY-MM-DD.dump
```

### Остановка

```bash
docker compose --env-file .env.prod -f docker-compose.prod.yml down
```

Данные (тома `pg_data`, `redis_data`) остаются. **`down -v` удаляет тома — то есть всю базу.**

### Настройки, которые можно менять в `.env.prod`

| Переменная | По умолчанию | Что |
|---|---|---|
| `HTTP_PORT`, `HTTPS_PORT` | 80, 443 | порты nginx на хосте |
| `EDGE_SUBNET` | 172.30.240.0/24 | подсеть внешней docker-сети — сменить, если пересекается с сетями хоста |
| `LOG_LEVEL` | info | `debug` — подробнее |
| `SCHEDULER_ENABLED` и `*_INTERVAL_SECONDS` | см. шаблон | планировщик: проверки, сверка, истечение доступов, чистка (0 — правило выключено) |
| `JOB_RETENTION_DAYS`, `AUDIT_RETENTION_DAYS` | 90, 365 | сколько хранить задачи и журнал (0 — вечно) |
| `LOGIN_*`, `REFRESH_*` | см. шаблон | лимиты попыток входа |

## Частые проблемы

| Симптом | Причина и решение |
|---|---|
| API не стартует: `JWT_SECRET_KEY must be at least 32 random characters` | в `.env` осталась заглушка из шаблона — сгенерируйте ключ (шаг 3) |
| `ModuleNotFoundError: No module named 'core'` | API запущен без `--app-dir src`, или скрипт — без `PYTHONPATH=src` |
| скрипт не видит `.env` (ошибки про `DATABASE_URL`) | скрипты запускаются **из корня** репозитория — `.env` ищется в текущей папке |
| задачи висят «В очереди» | не запущен воркер |
| вход проходит, но после перезагрузки страницы снова форма входа (dev) | в `.env` нет `COOKIE_SECURE=false`: по http браузер не сохраняет cookie с флагом Secure |
| dev-фронтенд: ошибки сети на `/api` | не запущен API на `:8000` — Vite проксирует туда |
| prod: `migrate` упал, api/worker не стартуют | `docker compose ... logs migrate` — обычно неверный `POSTGRES_*` или нестандартные символы в пароле |
| prod: nginx не стартует | нет `certs/fullchain.pem` / `certs/privkey.pem` |
| prod: «порт занят» | на хосте уже что-то слушает 80/443 — освободите или задайте `HTTP_PORT`/`HTTPS_PORT` (при нестандартном HTTPS-порте редирект с http уводит на 443 без порта — открывайте сразу `https://…:<порт>`) |
| задача сервера упала с `Host key of … is not pinned` | на карточке сервера закрепите ключ хоста (первый шаг подготовки) — пароль уходит только на сервер с закреплённым ключом |
| установщик или `./panel` пишет «нужен Docker Compose 2.24 или новее» | обновите пакет `docker-compose-plugin`; текущую версию покажет `docker compose version` |
| бот не отвечает или не выходит на связь с панелью | `./panel logs bot` (на другом сервере: `docker compose -f bot/docker-compose.yml logs bot`); проверьте исходящий порт 443 до `api.telegram.org` и адрес панели |
