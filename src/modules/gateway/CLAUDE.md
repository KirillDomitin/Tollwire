# modules/gateway — выходы шлюза (этап 24.2)

Шлюз (протокол `AMNEZIA_GATEWAY`, контейнер `vpn-admin-gw`, см. `infrastructure/vpn/CLAUDE.md`) - клиент своих
«выходов»: зарубежных серверов панели с протоколом `AMNEZIA_WG`. Для каждого выхода панель создаёт на нём
«внутреннего клиента» обычным `create_client` и поднимает на шлюзе интерфейс `gwx<слот>` с конфигом этого клиента.
Какой клиент шлюза идёт через какой выход - этап 24.3; здесь выходы только подключаются и снимаются.

## Модель `gateway_exits`

`gateway_protocol_id` (FK `protocols.id` CASCADE - шлюз снимают, строки уходят), `exit_protocol_id` (FK RESTRICT -
пока выход подключён, его протокол и сервер не удалить), `slot` (1..200, UNIQUE в пределах шлюза), `weight` (1..100,
по умолчанию 1), `max_clients` (NULL - без предела), `state` (`ExitState`, VARCHAR: pending / peer_created / active /
draining / removing), `health` (ok / stale / no_handshake / down, NULL - не сверяли), `last_handshake_at`,
`checked_at`, внутренний клиент: `client_public_key`, `client_address`, `encrypted_config` (Fernet, NULL до
`peer_created`). UNIQUE `(gateway_protocol_id, exit_protocol_id)` - выход подключён к шлюзу один раз; один выход может
обслуживать несколько шлюзов. Слот - наименьший свободный (`free_slot`), при постановке протокол шлюза блокируется
`FOR UPDATE`, поэтому два одновременных POST не возьмут один слот. Имя интерфейса, файла и номер таблицы строятся
только из целого слота (`gateway_config.py`).

## API (`/api/v1/servers/{server_id}/gateway/exits`, `api/v1/router.py`)

| Метод | Право | Что |
|---|---|---|
| `GET` | `servers:read` | Выходы по слотам: `id, exit_server_id, exit_server_name, slot, state, health, last_handshake_at, checked_at, weight, max_clients`. Ключей, адреса и конфига внутреннего клиента нет. Нет шлюза - `[]`, нет сервера - 404. |
| `POST` | `servers:manage` | `{exit_server_id, weight=1, max_clients=null}` -> 202 `JobRead` (`gateway_add_exit`). Строка выхода создаётся сразу в `pending`. |
| `PATCH /{exit_id}` | `servers:manage` | `{weight?, max_clients?}` - только БД, без задачи; аудит `gateway_exit_updated` (только реальные изменения); `weight: null` - 422, `max_clients: null` снимает предел. |
| `DELETE /{exit_id}` | `servers:manage` | -> 202 (`gateway_remove_exit`); выход сразу в `draining`. |

Коды POST: 404 - нет сервера или сервера-выхода; 422 - выход = сам шлюз, вес/предел вне диапазона; 409 - нет SSH-учётки
(шлюза или выхода), на сервере нет шлюза, на выходе нет `AMNEZIA_WG` (или его порт неизвестен), выход сам шлюз, выход уже
добавлен, по выходу идёт незавершённая задача, слотов не осталось. Выход, у которого добавление не удалось (`pending`,
`peer_created`) и задачи нет, ставится повторно тем же POST (тот же слот, вес и предел обновляются). DELETE: 404 - нет
выхода у этого шлюза, 409 - по выходу идёт задача; повтор после упавшей задачи - снова DELETE.

## Задачи (`service.py`, воркер под `ServerLock` шлюза; выход блокируется внутри, порядок всегда шлюз -> выход)

`Job.params`: `exit_id`, `exit_server_id`, `slot`, `weight` (последние три - только для аудита; ключей нет).

- `gateway_add_exit` (`run_add`), две фазы с сохранённым состоянием, повтор идемпотентен:
  1. `pending`: под `ServerLock(выхода)` клиент `gw-<12 hex id строки>` на `AmneziaWGProvider` выхода; если клиент с таким
     именем уже есть (прошлая попытка создала, но commit не дошёл) - он снимается и создаётся заново; ключ, адрес и
     зашифрованный конфиг сохранены, `peer_created`, commit.
  2. `peer_created`: `apply_exits` на шлюзе (Endpoint = `host` сервера-выхода + порт его `AMNEZIA_WG`), `active`, commit.
  Занятый выход - `ServerBusyError`, воркер возвращает задачу в очередь (пауза 1 с); фаза 1 при этом уже сохранена.
  В конце клиентам шлюза без выхода назначается выход (`assign_unassigned`). Результат: `{exit_id, exit_server_id,
  slot, assigned}`.
- `gateway_remove_exit` (`run_remove`): `draining` -> `drain()` (перенос клиентов на другие выходы, 24.3; счётчики
  `moved` / `unassigned` в результате и в аудите) -> `removing` -> `remove_exit(slot)` на шлюзе -> `revoke_client` внутреннего клиента на выходе под
  `ServerLock(выхода)` -> строка удалена. Выход недоступен по SSH - туннель снят, строка удалена, `peer_revoked: false`;
  оставшегося `gw-*` снимет sync выхода. Строки уже нет - успех (`already_removed`).

## Назначение выходов клиентам (`assignment.py`, `balancer.py`, этап 24.3)

Весь трафик клиента шлюза идёт через выход, назначенный клиенту. Нет назначения - нет метки - нет правила - срабатывает
kill-switch (`prohibit`): у клиента нет интернета и нет утечки.

- **Таблица `gateway_assignments`**: `credential_id` (PK, FK `vpn_credentials` CASCADE), `exit_id` (FK `gateway_exits`
  CASCADE), `pinned_exit_id` (FK SET NULL, задел под 24.5, пока не используется), `assigned_at`, `reason`
  (`issue` / `drain` / `failover` / `manual` / `sync`). БД - источник правды.
- **`pick_exit(candidates)`** (`balancer.py`, чистая функция): кандидаты - выходы `ACTIVE`, у которых health не `down` и
  не `stale` (нет сверки или нет рукопожатия - годятся), с `assigned < max_clients`; выигрывает минимум
  `(assigned + 1) / weight` (точная дробь), ничья - меньший слот; никого - `None`. Порядок кандидатов не влияет.
- **Готовность шлюза (`_ready`)**: перед любым применением карты (выдача, отзыв, `assign_unassigned`, перенос, sync) сервис
  ВСЕГДА вызывает идемпотентный `install()` шлюза: он дочиняет `start.sh` (цепочка, три прыжка PREROUTING, защита FORWARD),
  правила, политику перезапуска и пересоздаёт контейнер, созданный с устаревшими sysctl. Существования цепочки `GW_ASSIGN`
  для этого недостаточно: `iptables-restore` создаёт её и без прыжков, поэтому провайдер отказывается применять карту без
  прыжков (`apply_assignments`), а `assignments_in_sync` и health-проверка `assignments` требуют прыжки в `PREROUTING` и
  `ip rule` метки у поднятых выходов. Пересоздание контейнера (рвёт всех клиентов) пишется в аудит
  `gateway_container_recreated` (meta `server_id`, `reason: sysctl_mismatch`) и в отчёт sync (`container_recreated`);
  неудачный запуск после `stop && rm` повторяется один раз, второй сбой - понятная ошибка (контейнера нет, это видно в
  health и sync).
- **`GatewayAssignmentService`** (всё под `ServerLock` шлюза):
  - `attach(credential)` - выбрать выход (health берётся с шлюза сейчас, по рукопожатию), записать назначение
    (`issue`), commit, применить ПОЛНУЮ карту живых назначений, собранную из БД заново (не инкрементом: отозванный клиент и
    переиспользованный адрес не оставляют следов). Нет исправных выходов - `None`: клиент остаётся с выданным конфигом, но
    без выхода; выход ему назначит `assign_unassigned` при добавлении выхода (`run_add`) или в sync. Повтор для уже
    назначенного клиента применяет карту заново (чинит упавшее применение).
  - `detach(credential)` - снять назначение отозванного клиента и применить карту.
  - `assign_unassigned(gateway)` - выходы всем живым клиентам без назначения (причина `issue`, в sync `sync`).
  - `drain(exit)` - сначала убираются назначения отозванных, затем перенос клиентов снимаемого выхода по `pick_exit` на
    остальные (`drain`). Порядок: изменения БД -> flush -> применение карты -> commit: применение упало - ничего не
    сохранено, повтор считает тот же перенос; карта применяется ВСЕГДА (в том числе когда переносить некого), так что на
    шлюзе не остаётся правил с меткой удалённого выхода. Других подходящих выходов нет - назначение удаляется (kill-switch)
    и пишется `gateway_client_unassigned` (meta `credential_id`, `slot`). Счётчики `moved` / `unassigned` копятся в строке
    выхода (`drained_moved`, `drained_unassigned`) и переживают повторы задачи.
  - `estimate_unassigned(exit)` - сколько клиентов останется без выхода (БД, `pick_exit` на копии состояния, без SSH).
  - `reconcile(gateway, provider, issues)` - вызывается sync'ом шлюза: чистит назначения отозванных, пересоздаёт туннели
    `ACTIVE`-выходов с устаревшим конфигом (`apply_exits`, нужно после обновления панели: правило метки в PostUp),
    назначает клиентов без выхода, сравнивает карту на шлюзе (цепочка `GW_ASSIGN` и файл `assign.rules`) с БД и при
    расхождении применяет карту из БД (issue "Client assignments on the gateway differed from the DB and were re-applied").
    Цепочки нет (start.sh прежней версии) - сначала `install()` дочинит скрипт и правила.
- **Интеграция**: `VPNCredentialService.provision` (одна ветка для `AMNEZIA_GATEWAY`, после commit credential'а;
  повтор задачи для уже выданного клиента тоже назначает выход) и `deprovision` (после commit отзыва) в `access/service.py`.
  Сбой применения карты (SSH, `--test`) роняет задачу, но выданный конфиг и запись назначения остаются; sync применит карту
  из БД. Остальные протоколы и импорт Amnezia не затронуты.
- **Подтверждение снятия**: `DELETE .../exits/{id}` отвечает 409 с числом клиентов, если после переноса часть клиентов
  останется без выхода (снимается последний выход или у остальных нет места по `max_clients`); `?force=true`
  (`servers:manage`) подтверждает, задача идёт, а каждый оставшийся без выхода клиент попадает в аудит.
- **Карта**: `build_map_checked` отбрасывает адрес вне подсети клиентов, сети/broadcast/адрес шлюза и повтор адреса (карта не
  падает целиком, число пропущенных - в `issues` sync и `assignments.skipped`; адреса в журнал не пишутся);
  `render_assign_rules` по-прежнему строгий.
- **API**: в `GET .../gateway/exits` у выхода `assigned_clients`; `GET .../gateway/assignments` (`servers:read`) - список
  `credential_id, exit_id, slot, reason, assigned_at` без адресов и ключей.
- **Аудит**: `gateway_client_assigned` (сущность - credential; meta `credential_id`, `slot`, `reason`; адресов и ключей нет);
  в `gateway_exit_remove_completed` - счётчики `moved` и `unassigned`.
- **Известные ограничения**: упавший выход (health `down`) клиентов не теряет и не переносит - у них нет интернета, пока
  выход не вернётся (failover - 24.5); закрепление (`pinned_exit_id`, его индекс и удаление) и ручное назначение (`manual`)
  не реализованы; `no_handshake` считается годным до failover; при переносе клиента conntrack не чистится (в образе нет
  conntrack-tools): уже установленные соединения остаются на прежнем выходе, UDP-потоки после смены уйдут в kill-switch
  до конца таймаута и на прикладном уровне переподключатся; в API нет статуса клиента «без выхода» - его покажет UI 24.6
  из `assignments`.

## Россия напрямую (`ru.py`, этап 24.4)

Клиенты шлюза, идущие на российские адреса, выходят с адреса шлюза (MASQUERADE `-s 10.77.0.0/22 -o eth0` уже есть),
остальной трафик - через назначенный выход (24.3). Список - `modules/geoip/CLAUDE.md`; работа с сервером и скрипт -
`infrastructure/vpn/CLAUDE.md`.

- **Маршрутизация на шлюзе**: правило `ip rule` приоритета 100 `from 10.77.0.0/22 lookup 200|201` стоит РАНЬШЕ меток
  выходов (1000), поэтому российские адреса уходят в `eth0` минуя `gwx*`; всё, чего нет в таблице, падает в метки выходов, а
  без метки - в kill-switch (9000). Таблицы 200 и 201 используются по очереди: запасная заполняется, правило переключается.
- **`GatewayRuService`** (`ru.py`): `schedule_apply(server_id)` (быстрые проверки по БД: 404 нет сервера; 409 нет SSH-учётки,
  шлюза, активного списка или незавершённой такой же задачи; затем 202), `run_apply(job)` (воркер под `ServerLock` шлюза:
  эффективный список -> `apply_ru`; результат `{routes, table, prefixes}`), `ensure(provider, issues)` (сверка: есть активный
  список, а маршрутов на шлюзе не столько, сколько в эффективном списке, - применить; сбой - issue, не исключение),
  `health_check(provider)` (проверка `ru`) и `ensure_server(server_id)` (после установки шлюза, ошибки только в лог).
- **Задача `gateway_apply_ru`**: `server_id` = шлюз, без `params`; ставится API (`POST /api/v1/servers/{id}/gateway/ru/apply`,
  `servers:manage`, 202) и `GeoipService` после активации списка / изменения исключений (по одной на шлюз, без дублей).
  Занятый сервер - задача возвращается в очередь. Аудит: `gateway_ru_applied` (`routes`) и `gateway_ru_apply_failed`.
- **Сверка списка**: скрипт после успеха записывает в `ru.applied` отпечаток (первая строка `# sha256=<hex>` файла
  `ru.prefixes`, хэш префиксов ниже; ставит панель), `ru_status().digest` его читает. Список «применён», если совпали
  ОТПЕЧАТОК и число маршрутов (одного числа мало: другой список того же размера прошёл бы незамеченным).
- **Эффективный список шлюза** вычитает зарезервированные диапазоны и адреса самого шлюза и его выходов (/32): DIRECT-исключение,
  накрывающее адрес выхода или SSH-хоста, не ломает туннели и управление (сервис такое исключение и не принимает - 422).
- **Sync** шлюза (`servers/sync.py::_reconcile_ru`): отчёт `ru` = `{active_list, expected, routes, applied}`; нет активного
  списка - `{active_list: false}` и больше ничего. Расхождение отпечатка или числа маршрутов (таблица пуста после пересоздания
  контейнера, устарела или от другого списка) чинится применением списка. Сбой - issue "Failed to apply the Russian routes", sync
  не падает; испорченный список в БД - issue и `{error: true}` (текст без строк списка).
- **Health**: проверка `ru` добавляется, ТОЛЬКО когда есть активный список (иначе шлюз вечно был бы DEGRADED), «пройдена»,
  если применён именно эффективный список (отпечаток и число маршрутов); испорченный список - проверка не пройдена.
- **Установка**: `install_protocol` воркера после установки шлюза зовёт `ensure_server`: переустановленный шлюз получает
  маршруты обратно (если `ru.prefixes` сохранился на хосте, `start.sh` загрузит его сам); если активного списка ещё нет,
  ставится `GEOIP_UPDATE` (без дублей).
- **Известные ограничения**: страна по RIPE - страна регистрации блока (хостеры, CDN: российские сервисы за зарубежным CDN
  пойдут через выход; чинится `direct`-исключением); DNS клиентов идёт через выход; пока список применяется (около 4 секунд на
  8,6 тыс. маршрутов), новые соединения клиентов не страдают (в любой момент есть ровно одно рабочее правило 100), но
  уже установленные соединения к адресам, ушедшим из списка, продолжат идти с адреса шлюза до конца своей жизни; список
  применяется только к клиентам шлюза (обычный `amnezia_wg` не затронут); IPv6 не поддержан.

## Аудит

`gateway_exit_add_started/completed/failed`, `gateway_exit_remove_started/completed/failed` (через таблицы
`_STARTED/_COMPLETED/_FAILED` в `jobs/service.py`, сущность `server` = шлюз) и `gateway_exit_updated`. Meta: `job_id`,
`exit_id`, `exit_server_id`, `slot`, `weight` (у add), `error`; для PATCH - `changes`. Ключей и конфигов нет.

## Защиты и связи

- Нельзя удалить сервер-выход и снять с него `AMNEZIA_WG`, пока на него ссылается `gateway_exits`
  (`LiveCredentialExistsError` -> 409; в `ServerService.schedule/delete` и повторно в `protocol_uninstall` воркера).
- Удаление сервера-шлюза и снятие протокола шлюза каскадом удаляют его выходы; клиенты `gw-*` на выходах остаются, их
  снимает sync выхода.
- Sync выхода (`servers/sync.py`): `gw-*` с записью в состоянии peer_created / active / draining - живой (потерянный
  возвращается `restore_client` по сохранённому конфигу); `gw-*` без такой записи (в том числе у `removing`) - сирота и
  снимается; прочее не трогается.
- Sync шлюза: отчёт `exits` и `issues` ("Exit gwxN is down/missing on the gateway" для `active` без интерфейса, "Unknown
  exit tunnel" для туннеля без записи), обновление `health` / `last_handshake_at` / `checked_at`. Автодействий нет
  (failover - 24.5). Health-задача шлюза обновляет те же поля.

## Известные ограничения

- Снять выход при навсегда недоступном шлюзе нельзя (задача снятия падает на SSH к шлюзу); такой выход уходит вместе с
  удалением сервера-шлюза (строки выходов удаляются каскадом, внутренних клиентов `gw-*` снимет sync выхода). Принудительного
  `?force=true` нет.
- Health-задача шлюза опрашивает туннели второй раз (`exit_status` для БД поверх проверки провайдера) - лишние две команды на
  выход; осознанная неоптимальность.
- Имя внутреннего клиента - строго `gw-` + 12 hex (`is_exit_client_name`): sync снимает только такие; чужие `gw-*` (например,
  `gw-office` из приложения AmneziaVPN) попадают в `foreign` и не трогаются.
- Сбой чтения туннелей (`awg show interfaces`) во время sync шлюза не теряет отчёт по клиентам: в `issues` -
  "Failed to list exit tunnels on the gateway", `exits` пуст, health строк не меняется.
- POST и DELETE берут блокировку строки протокола шлюза (`lock_gateway`): ADD и REMOVE одного выхода не ставятся вместе.
