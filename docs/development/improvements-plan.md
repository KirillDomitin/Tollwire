# План доработок управления VPN

## 1. Надёжное удаление пользователей (пункты 1 и 5)

- Исходный HEAD: `871f5af05f8b74336eb51212b74469341e07dff1`; рабочее дерево до начала чистое.
- Проверить удаление двух пользователей с одинаковыми именами, включая `Admin [Android (16.0)]`.
- Установить точный симптом сбоя в интерфейсе и ответ API.
- Исправить подтверждённую причину в ответственном слое.
- Критерий: удаляется только выбранная запись по UUID; другая запись и её доступ сохраняются.
- Сохранить запрет удаления пользователя с живыми VPN-клиентами: сначала отзыв доступа.
- Проверки: регрессионный сценарий, проверки затронутого слоя, ревью diff.

Исходная проверка: веб-панель уже отправляет UUID в DELETE `/api/v1/vpn-users/{user_id}`;
сервис ищет запись по UUID, провайдер отзывает peer по публичному ключу.
Причина неактивной кнопки подтверждена ответом API: `username` содержит два пробела
в `Admin [Android  (16.0)]`. HTML схлопывает пробелы в видимой подписи, а поле сравнивалось
с исходной строкой посимвольно. Копирование видимого текста не обеспечивало совпадения.

Подтверждение удаления переведено с имени на UUID пользователя. Имя остаётся в заголовке,
строка для подтверждения отображает UUID. Регрессионные сценарии проверяют переход из списка
одноимённых пользователей, блокировку кнопки при вводе имени, включение при вводе UUID,
DELETE выбранного ID и сохранение другой записи в списке. Включены точное проблемное имя,
обычные имена и невидимые символы. Отдельно проверены сообщение HTTP 409 и сохранение карточки.
API в этих тестах подменён: настоящие записи и VPN-доступы не удалялись.

## 2. Last handshake и трафик клиентов, затем сортировка (пункты 2 и 3)

- База этапа: `f666835ede880575ca7a88be9c266acf70c2a1f0`, исходное рабочее дерево чистое.
- В текущий блок включены последнее рукопожатие и скачанные/отправленные байты каждого VPN-клиента.
- Направления показывать со стороны клиента: скачано = TX сервера, отправлено = RX сервера.
- Принято: текущие счётчики VPN, без накопления и миграции БД; подпись «с последнего сброса VPN».
- Счётчики могут обнулиться при перезапуске VPN или пересоздании peer'а; начало периода неизвестно.
- Привязывать статистику по серверу, протоколу и ключу credential, а не по имени пользователя.
- Проверить доступность времени handshake в текущем сборе мониторинга и API клиентов.
- Показать последнее рукопожатие: относительное время, точная дата, отсутствие данных.
- Реализованы поминутный сбор через провайдер, Redis-снимки и cache-only API с `servers:read`.
- В карточке устройства показываются время замера, handshake и байты; устаревшие и отсутствующие данные различаются.
- Контракт и проверки: [статистика клиентов](../monitoring/client-metrics.md). Живой VPN-прогон ещё не подтверждён.
- Добавить сортировку по заголовкам: повторный клик меняет направление, состояние доступно скринридеру.
- Критерий: корректный порядок всего набора, определённое место пустых значений; сортировка работает с поиском.
- Если потребуется новый существенный API-контракт — сначала архитектурное решение.

## 3. Клиенты сервера (пункт 4)

- По клику на счётчик открыть клиентов выбранного сервера с фильтрами онлайн/офлайн.
- Использовать единое правило онлайна и показывать время актуальности данных.
- Критерий: счётчик и список согласованы, переход не смешивает клиентов разных серверов.

## 4. До пяти устройств (пункт 9)

- До реализации согласовать владельца лимита и обработку уже существующих пользователей с более чем пятью устройствами.
- Проверить модель устройств и пути создания через панель, бот и импорт.
- Архитектурное решение и тесты до реализации; лимит проверяется на сервере с учётом конкурентных запросов.

## 5. Шлюз, скорость и новые протоколы (пункты 8, 7 и 6)

- Уточнить сценарий смены выхода шлюза через бот; проверить существующий механизм назначения.
- Согласовать измеряемые показатели скорости, направление и допустимую нагрузку теста.
- Выбрать один дополнительный протокол и его обязательные операции.
- Для каждого нового механизма: architect → решение пользователя → tester → реализация → reviewer.
- Реальные серверы использовать только с явного согласия.

Каждый этап завершается отдельно проверками и результатом; коммиты — по поручению.
