# Обновление готовыми релизами

Первая установка остаётся за `install.sh`. Для обновления существующей панели workflow
`Build release` собирает и проверяет один коммит, публикует образы в GHCR и выдаёт архив.
GitHub не подключается к серверу: применение релиза запускает оператор.

## Подготовка релиза

1. Изменения должны попасть в `master`; дождитесь успешного запуска `CI` для push этого коммита.
2. В GitHub Actions откройте `Build release`, выберите ветку `master` и передайте полный SHA
   коммита в поле `commit`. Коммит должен принадлежать истории `master`.
3. Дождитесь успешного workflow и скачайте его artifact `tollwire-<SHA>`.
   Внутри находится `tollwire-<SHA>.tar.gz` с каталогом `release/`.

Workflow проверяет исходный SHA и результат CI, собирает app/web/bot под `linux/amd64`, затем
проверяет production-образы. Проверки включают nginx-конфигурацию с временным сертификатом,
импорты API/worker, миграцию на пустой БД, запуск API и worker, импорт бота и веб-статику.
БД и Redis изолированы, production-секреты и VPN-серверы не используются. Только после этого
образы публикуются, а bundle получает точные digest.

`release.json` содержит версию формата, SHA, платформу, образы app/web/bot, Alembic heads и
SHA256 файлов релиза. Проверяются структура, имена репозиториев, digest и содержимое файлов.
Контрольные суммы внутри архива не удостоверяют издателя: используйте artifact доверенного
запуска своего репозитория, а не архив из стороннего источника.

## Применение на сервере

Требования: существующая исправная установка, Linux x86-64, Python 3.10+, Bash, Docker с
Compose 2.24+, доступ к GHCR и не менее 512 МиБ свободного места. Дополнительно нужно место
для образов и полного дампа БД. Если образы закрытые, заранее настройте доступ Docker на
сервере к соответствующим пакетам GHCR. Данные доступа в bundle не входят.

Распакуйте архив **вне каталога установки**, не заменяя корневые Compose/nginx-файлы.
Это необходимо для сохранения исходной конфигурации первого отката:

```bash
mkdir -p /tmp/tollwire-release
tar -xzf tollwire-<SHA>.tar.gz -C /tmp/tollwire-release
TOLLWIRE_ROOT=/opt/tollwire bash /tmp/tollwire-release/release/scripts/deploy.sh /tmp/tollwire-release/release
```

`/opt/tollwire` здесь — каталог существующей панели. `TOLLWIRE_ROOT` обязателен при запуске
скриптов из внешнего bundle. Скрипт не делает `git pull`, не собирает образы и не меняет
секреты, сертификаты, PostgreSQL/Redis или их тома.

Порядок обновления:

1. Блокировка параллельных запусков, проверка установки и manifest. При первом обновлении
   сохраняются фактические ID старых образов, схема БД и копии Compose/nginx.
2. Загрузка нужных образов по digest и проверка целевой Compose-конфигурации до простоя.
3. Остановка nginx, API и включённого локального бота; штатный SIGTERM worker с ожиданием
   до 90 секунд. Неудачный drain или оставшиеся `RUNNING`-задачи блокируют миграцию.
4. Приватный `pg_dump -Fc` и проверка каталога архива через `pg_restore --list`.
5. Однократная миграция выбранным app-образом, запуск API/worker, затем nginx и локального
   бота, если он был включён.
6. Проверка образов, API, внутреннего HTTPS, ссылок на JS/CSS и стабильности контейнеров.
   Только после успеха обновляются записи успешного релиза.

Во время обновления панель недоступна. Проверка внутреннего HTTPS не подтверждает внешний
DNS, маршрут и соответствие имени сертификату: после обновления проверьте обычный URL панели.
Удалённый Telegram-бот этим релизом не обновляется. Ручное изменение локального бота или
образов после релиза может вызвать отказ из-за расхождения с сохранённым состоянием.

Повтор того же SHA с теми же образами и файлами проверяет работоспособность и завершает работу
без повторной миграции. Подмена digest или хешей при прежнем SHA отклоняется.

## Состояние и резервные копии

В корне установки создаётся приватный `.deploy/`, исключённый из Git:

| Путь | Назначение |
|---|---|
| `current.json` | Текущий успешный релиз или исходная legacy-установка |
| `previous.json` | Предыдущий успешный набор образов и конфигурации |
| `attempt.json` | Фаза попытки, исходный/целевой релизы, путь backup и имя migrator |
| `releases/` | Снимки Compose/nginx и override с закреплёнными образами |
| `backups/<ID>/database.dump` | Проверенный дамп непосредственно перед переключением |
| `legacy-panel` | Исходный `panel` до установки защитного префикса, права 0600 |
| `lock` | Блокировка обновления и отката |

Дампы деплоя не удаляются обычной ротацией `panel backup`. Не удаляйте снимки, backup или
старые образы, пока они нужны для возврата; политику освобождения места задаёт оператор.
Секреты и ключ шифрования в резервную копию не входят — храните их отдельно, как описано
в [INSTALL.md](../../INSTALL.md#backup).

Обычный backup остаётся доступен:

```bash
TOLLWIRE_ROOT=/opt/tollwire bash /tmp/tollwire-release/release/scripts/backup.sh
```

Это обёртка корневого `panel backup`. В новой версии `panel backup --print-path` выводит
в stdout только путь созданного дампа; сообщения идут в stderr. Старый `panel` может не знать
этот флаг. Сам deploy от него не зависит и создаёт проверенный дамп отдельно.

## Откат

Для возврата предыдущего успешного релиза используйте сохранённые скрипты доверенного bundle:

```bash
TOLLWIRE_ROOT=/opt/tollwire bash /tmp/tollwire-release/release/scripts/rollback.sh
```

Откат разрешён только при совпадении фактических Alembic revisions с требуемой схемой
предыдущего релиза и наличии его образов. Он также делает backup и проверяет запуск.
Текущие данные БД сохраняются: автоматического restore или downgrade нет.

При отказе обновления старая версия возвращается автоматически только при подтверждённой
прежней схеме. Если схема изменилась, неизвестна или завершение миграции не подтверждено,
сервисы остаются остановленными. Именованный migrator принудительно удаляется при ошибке
команды; если результат операции нельзя установить, автоматический рестарт запрещён.

Прерванная попытка блокирует новые deploy/rollback до ручного восстановления. Сначала
прочитайте `.deploy/attempt.json`, `current.json` и `previous.json`; установите фактическую
схему БД, состояние migrator из записи попытки и наличие backup. Выберите совместимый релиз
или отдельную процедуру восстановления БД, затем согласуйте рабочие сервисы и состояние.
Не удаляйте `attempt.json` ради обхода проверки и не запускайте старое приложение поверх
непроверенной схемы. Restore дампа после открытия записи удалит более новые данные;
изменения на внешних VPN-серверах дамп БД не отменяет.

## Совместимость старых команд

Перед созданием исходного release-state скрипт атомарно добавляет в существующий `panel`
фиксированный Bash-префикс. Он блокирует legacy update/restore/bot при наличии
`.deploy/current.json`. Исходный файл сохраняется в `.deploy/legacy-panel` с правами 0600;
остальное тело `panel` и его библиотеки остаются прежними.

Корневой checkout, `install.sh` и теги `latest` не обновляются. После перехода на релизы
**не используйте повторный `install.sh` или ручной `compose up --build`**: они могут запустить
старый код и обойти выбранный manifest. Защитный префикс не удаляйте ради запуска старых
`panel update`, `panel restore` или `panel bot`: старые bot-команды также могут пересоздать
зависимости из корневого Compose. Работа уже включённого бота сохраняется; для изменения
его размещения или CLI-обслуживания нужна отдельная процедура через текущий release snapshot.

Для обновления и отката используйте release-скрипты. Первую установку и прежний режим
обновления до перехода на релизы описывает [INSTALL.md](../../INSTALL.md#updating).
