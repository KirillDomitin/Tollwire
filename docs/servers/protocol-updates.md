# Образы протоколов: проверка и обновление

Поддерживаются только установленные панелью `amnezia_wg` и `amnezia_gateway`. Контейнеры приложения
AmneziaVPN (`amnezia_app_awg`, `amnezia_app_awg2`) не обновляются. Источник фиксирован:
`amneziavpn/amneziawg-go:latest`; произвольный образ, тег или URL в API не принимается. `latest` означает
последнюю публикацию канала, а не сравнение номеров стабильных релизов. Обычная установка по-прежнему
использует закреплённый `AMNEZIAWG_IMAGE`.

## Проверка доступности

Планировщик проверяет календарь раз в минуту и запускает опрос ежедневно после **03:00 Europe/Moscow**.
После простоя выполняется одна проверка за текущую дату; прошлые дни не воспроизводятся. Redis-ключ даты
исключает дубли между воркерами и живёт двое суток. При исключении или отмене сканирования свой ключ
освобождается для повторной попытки. Это не расписание автоматического обновления контейнеров.

Выбираются серверы с SSH-учёткой и протоколом, кроме `INSTALLING`. Одновременно опрашиваются не более пяти
серверов; внешний срок одного опроса — 90 с, сетевой части сервиса — 75 с. У каждого сервера своя сессия БД,
перед SSH транзакция завершается. Ошибка отдельного сервера не мешает остальным; общие ошибки БД/Redis
прерывают правило.

`VPNProvider.image_info()` проверяет принадлежность контейнера и читает его фактический image ID, затем
платформу этого образа через Docker inspect. Проверка не выполняет pull, stop или run, не читает VPN-конфиг
и не меняет `health_status`. Registry-клиент читает metadata фиксированных Docker Hub/auth-адресов;
слои не скачиваются, redirects запрещены, размер ответа и время ограничены. Metadata кешируются в Redis
на 300 с с блокировкой повторных запросов.

Для multiarch index выбирается manifest платформы установленного образа; его `config.digest` сравнивается
с фактическим image ID контейнера. Digest индекса не сравнивается с image ID. Неизвестная или неоднозначная
платформа даёт `unknown`.

## API

Пути относительно `/api/v1/servers`:

| Метод и путь | Право | Результат |
|---|---|---|
| `GET /{id}/protocol/updates` | `servers:read` | `200 ProtocolUpdatesRead`, только кеш, без SSH/registry |
| `POST /{id}/protocol/updates/check` | `servers:check` | `202 JobRead`, задача `CHECK_PROTOCOL_UPDATES` для протоколов сервера |
| `POST /{id}/protocol/update` | `servers:manage` | `202 JobRead`, задача `UPDATE_PROTOCOL` для одного протокола |

Обновление принимает необязательное тело `{"type": "amnezia_gateway"}` и/или query `?type=amnezia_gateway`.
Без типа выбирается `amnezia_wg`; несовпадение тела и query, APP-тип или неизвестный тип — 422. Нет сервера
или установленного протокола — 404; нет SSH-учётки или уже есть незавершённая задача того же типа на сервере —
409. Постановка новых задач сериализована блокировкой строки сервера в БД. Наличие протокола повторно
проверяется воркером под `ServerLock`.

`ProtocolUpdatesRead` и результат задачи проверки имеют форму `{"protocols": [...]}`. Наблюдение содержит
`protocol_id`, `protocol_type`, `status`, `stale`, `checked_at`, `last_attempt_at`, `current_image_id`,
`target_image_id`, `target_digest`, `reason`.

| status | Значение |
|---|---|
| `current` | Image ID совпадает с образом выбранной платформы канала latest |
| `available` | Image ID отличается; обновление запускает администратор |
| `unknown` | Нет достоверного результата или последняя попытка неуспешна |
| `unsupported` | Контейнер приложения, не обслуживаемый обновлением панели |

Успех хранится семь дней; после 26 часов помечается `stale`. Ошибка попытки переводит статус в `unknown`,
ставит `stale`, сохраняет прежние image-поля и время последнего успеха. Ошибки не продлевают срок хранения
последнего успеха. Нет кеша или Redis недоступен при чтении — `unknown` без сетевого опроса.
`reason` — фиксированный код: `server_unreachable`, `registry_unavailable`, `rate_limited`, `platform_unknown`,
`container_missing`, `update_in_progress`; stderr наружу не передаётся. Удалённые протоколы из кеша не выдаются.

Во время обновления результат скрывается как `unknown/stale`. Наблюдения помечены поколением обновления:
GET отклоняет запоздавшую запись, даже если обновление успело начаться и завершиться между запросами.
После завершения обновления кеш инвалидируется; после успешного commit задачи воркер ставит новую проверку.
Сбой этой проверки не отменяет успешное обновление.

## Замена контейнера и восстановление

`UPDATE_PROTOCOL` всегда имеет `params.protocol_type`, в том числе для обычного AWG. Выполняется под
`ServerLock`; записи протокола, клиентов и доступов не пересоздаются.

1. Проверить собственный работающий контейнер и конфиг. Скачать latest до остановки VPN, получить image ID
   и допустимый RepoDigest только доверенного репозитория. Совпадение image ID — `changed=false`, без перезапуска.
   Несколько RepoDigests одного образа допустимы; перед заменой выбранный digest проверяется на тот же image ID.
2. Сохранить каталог конфигурации в приватный соседний `<host_config_dir>-update-snapshot`, атомарно вести
   `.container-update.json`; metadata журнала не включается в снимок. Фазы: `preparing`, `prepared`, `replacing`,
   `verified`. Docker cidfile `.container-update-new.cid` фиксирует ID нового контейнера при потере ответа SSH.
3. Повторно проверить владельца/ID, остановить старый контейнер, переименовать в `<name>-update-backup`,
   создать новый по immutable digest с прежним портом и bind mount.
4. Проверить готовность, прежние peers и файлы; для шлюза — выходы, назначения, NAT, kill-switch и российские
   маршруты. Свежие handshake не требуются. После фазы `verified` удалить старый контейнер и служебные файлы.

Ошибка до остановки не меняет работающий VPN. Ошибка замены вызывает возврат прежнего контейнера и файлов,
но задача остаётся `FAILED`. Полный результат задачи содержит `protocol_type`, `changed`, `previous_image_id`, `target_image_id`,
`target_digest`, `rollback` (`not_needed`, `succeeded`, `failed`), `recovered`; ещё неизвестные ID могут быть null.
При отказе до подготовки отчёта в `Job.result` может остаться только `protocol_type`.
Аудит `protocol_update_started/completed/failed` содержит тип протокола и безопасный результат, без конфигов.

После обрыва следующий ручной update читает журнал и проверяет полные ID объектов. Незавершённая замена
восстанавливает прежний контейнер; неизвестные backup/ID или некорректный журнал требуют ручного разбора,
чужие объекты не удаляются. В фазе `verified` сохраняется уже работающий новый контейнер и завершается очистка:
последующие изменения клиентов не сверяются со старым снимком и не откатываются. Автономного восстановления
без повторного вызова нет. Не удалять журнал, cidfile или снимок вручную до выяснения фазы.

## Интерфейс и проверки

В «Обслуживании» состояние и время проверки показаны рядом с конкретным протоколом. «Проверить обновления»
доступно с `servers:check`; «Обновить контейнер» — с `servers:manage`, после предупреждения о разрыве VPN.
Устаревшие сведения отмечены отдельно. Журнал задач показывает замену/noop и результат отката. UI раз в минуту
читает кеш; задачи опрашиваются существующим механизмом, по завершении кеш перечитывается.

Перечень тестов — [protocol-updates.md](../tests/protocol-updates.md). Замена на реальном VPN-сервере требует
отдельного согласия: возможен краткий разрыв VPN и failover шлюза.
