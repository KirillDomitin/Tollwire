## Failover, ручной перенос и закрепление (`failover.py`, `balancer.py`, этап 24.5)

Выход шлюза отказал - клиенты сами переезжают на исправные выходы; админ может перенести клиента вручную и закрепить его за
выходом. Всё идёт через те же назначения и ту же полную карту (`apply_assignments`), что и в 24.3.

- **Здоровье выхода** (только ACTIVE-выходы с туннелем; PENDING / PEER_CREATED / DRAINING / REMOVING не участвуют). Проверка
  «хорошая» решается ТОЛЬКО по туннелю: интерфейс `gwxN` поднят и рукопожатие свежее
  (`ACTIVE_HANDSHAKE_WINDOW_SECONDS`, 180 с); нет интерфейса, устаревшее или отсутствующее рукопожатие - плохая. Состояние
  сервера-выхода (`servers.health_status`, обновляется редко и не зависит от туннеля) на решение не влияет: живой туннель
  с DOWN-сервером - не отказ. Колонки
  `gateway_exits.consecutive_failures`, `failure_notified` и `healthy_since` (чистая `next_health`, гистерезис): плохая проверка только растит
  счётчик; выход ОТКАЗАЛ при `FAILURE_THRESHOLD = 2` плохих подряд; первая хорошая проверка обнуляет счётчик, фиксирует
  `healthy_since` (начало непрерывной исправности; дальше не двигается) и, если выход был отказавшим, пишет
  `gateway_exit_recovered`. Выход с одной плохой проверкой («подозрительный») новых клиентов не получает и сам не считается
  отказавшим (`usable` плана - то же правило, что `GatewayAssignmentService._candidates` для новых клиентов).
- **Плохи ВСЕ ACTIVE-выходы сразу** (перезапуск контейнера шлюза: `awg show interfaces` пусто при коде 0; сбой самого шлюза;
  тотальный отказ): переносить некуда, поэтому счётчики НЕ растут (иначе через два тика у всех счётчик 2, первый поднявшийся
  получил бы всех клиентов - `max_clients` не защищает, возврата нет), failover не планируется, `healthy_since` сбрасывается,
  `health` помечается, рукопожатие не трогается. Переход «были исправные -> все плохи» (по прежнему health выходов) пишется один
  раз как `gateway_all_exits_down` (`server_id`, число выходов), без повтора на каждый тик; возврат - `gateway_exit_recovered`
  по каждому поднявшемуся. Шлюз с одним выходом поэтому никогда не делает failover, а только сообщает о простое.
- **Счётчик ведёт планировщик.** Ручная проверка (`POST .../check`, задача с `params.check`) обновляет health / рукопожатие, но
  НЕ увеличивает счётчик, если с прошлой проверки выхода прошло меньше половины `GATEWAY_WATCH_INTERVAL_SECONDS` (иначе «две
  подряд» превращались бы в две пробы с интервалом в секунды); правило `gateway_watch` считает всегда. В `GET .../exits` видны `health`, `last_handshake_at`, `healthy_since`; счётчик наружу не отдаётся.
- **Правило планировщика `gateway_watch`** (`scheduler.py::watch_gateways`, раз в 60 с, `GATEWAY_WATCH_INTERVAL_SECONDS`, 0 -
  выключено): шлюзы опрашиваются ПАРАЛЛЕЛЬНО (`asyncio.gather`, семафор `WATCH_CONCURRENCY` = 5, свой сеанс БД на шлюз) и каждый
  не дольше `WATCH_TIMEOUT_SECONDS` = 20 с: недоступные шлюзы не задерживают остальные правила планировщика; ошибка или срок одного
  шлюза не влияют на остальных и не меняют его счётчики. Для каждого шлюза с ACTIVE-выходами читает туннели по SSH (только чтение, без ServerLock), обновляет health /
  счётчики / `healthy_since` / `last_handshake_at` / `checked_at` и, если выход отказал / восстановился или `plan_failover`
  даёт переносы, ставит задачу `GATEWAY_APPLY` (`server_id` = шлюз, дедуп по незавершённой). Шлюзы без выходов не опрашиваются,
  ошибка SSH одного шлюза правило не роняет (счётчики остаются прежними - недоступность шлюза не отказ выхода).
- **Задача `GATEWAY_APPLY`** (`GatewayFailoverService.run_apply`, воркер под `ServerLock` шлюза): решение ПЕРЕСЧИТЫВАЕТСЯ по
  свежим данным БД (флагу из правила не доверяем); пустой план - шлюз не трогается вообще (ни SSH, ни apply), иначе порядок
  БД -> flush -> карта на шлюзе (один раз) -> commit. Карта не применилась - ничего не сохранено, следующая проверка
  планирует то же снова. `params.check` (кнопка «проверить сейчас») добавляет проверку выходов перед планом. Результат
  `{moved, returned, stranded}`.
- **`plan_failover(exits, assignments, pins, now, return_after)`** - чистая детерминированная функция, повтор плана по
  применённому состоянию пуст. Клиенты отказавших выходов переезжают на исправные через `pick_exit` (веса, `max_clients`;
  причина `failover`), ВСЕ затронутые за один проход. Незакреплённые остаются там, куда переехали (возврата нет).
  Закреплённые (`gateway_assignments.pinned_exit_id`) уезжают так же; когда закреплённый выход непрерывно исправен
  `return_after` (`GATEWAY_FAILOVER_RETURN_AFTER_SECONDS`, 600 с), возвращаются (`failover_return`), не больше 5 за проход
  (остальные - на следующих проходах; выход при этом не должен быть полон). Нет исправных выходов - ничего не меняется
  (kill-switch, клиенты без интернета и без утечки), клиенты считаются в `stranded`.
- **Аудит** (без ключей и адресов): `gateway_client_moved` (`credential_id`, `from_slot`, `to_slot`, `reason`: failover /
  failover_return / manual / pin / unpin), `gateway_failover` (`exit_id`, `slot`, `moved`, `unassigned`) - когда с отказавшего
  выхода кого-то перенесли, а «некуда деть» - один раз за отказ: признак `gateway_exits.failure_notified` (сбрасывается при
  восстановлении) не зависит от того, какая задача и когда отработала; `gateway_all_exits_down`, `gateway_exit_recovered`.
- **API**: `PATCH /api/v1/servers/{id}/gateway/assignments/{credential_id}` (`access:manage`), тело `{exit_id: uuid|null,
  pin: bool}`: перенос на указанный ACTIVE-выход этого шлюза (причина `manual`) и / или закрепление (`pin=true` - за целевым
  выходом, без `exit_id` - за текущим; `pin=false` снимает закрепление; `exit_id=null, pin=false` - только снять).
  Выполняется синхронно под `ServerLock` шлюза (прямой вызов сервиса из запроса, а не задача: ответ 200 сразу несёт итоговое
  назначение с `pinned_exit_id`). Порядок: готовность шлюза (`_ready`, при пересоздании контейнера коммитит) -> изменения в БД ->
  карта -> commit. Сбой SSH / Docker / применения - 502 с общим текстом (без путей и вывода команд), в БД ничего не сохранено.
  Ручной перенос не проверяет `max_clients` и счётчик отказов: проверяется только что выход ACTIVE, принадлежит этому шлюзу и не
  отказал (`consecutive_failures` меньше порога) - это осознанное решение админа. 404 - нет сервера / клиента этого шлюза / выхода этого шлюза; 409 - нет шлюза, клиент
  отозван или без выхода (для снятия/закрепления), выход не ACTIVE или отказал, шлюз занят; 422 - тело. Клиенту без
  назначения выход назначить вручную можно. `POST .../gateway/check` (`servers:check`) - «проверить сейчас»: 202 `JobRead`
  (`gateway_apply` с проверкой), 409 если такая задача уже идёт. `GET .../assignments` теперь отдаёт `pinned_exit_id`.
- **Известные ограничения**: нет перебалансировки по нагрузке (режим 3: клиенты остаются там, куда попали); упавший туннель не
  поднимается автоматически (панель только переносит клиентов); conntrack не чистится (установленные соединения на
  отказавшем выходе пропадут сами, новые идут через новый выход); отказ определяется по рукопожатию, поэтому здоровый, но
  простаивающий туннель держит рукопожатие свежим только keepalive (25 с, WireGuard пересогласует ключи ~раз в 2 минуты, окно
  180 с оставляет запас); недоступный шлюз - не отказ его выходов; закреплённый клиент возвращается только при непрерывной
  исправности выхода, любая плохая проверка обнуляет отсчёт `return_after`.
