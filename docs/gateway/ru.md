# Шлюз: «Россия напрямую» (этап 24.4)

## Россия напрямую (`ru.py`, этап 24.4)

Клиенты шлюза, идущие на российские адреса, выходят с адреса шлюза (MASQUERADE `-s 10.77.0.0/22 -o eth0` уже есть),
остальной трафик - через назначенный выход (24.3). Список - `modules/geoip/CLAUDE.md`; работа с сервером и скрипт -
`infrastructure/vpn/CLAUDE.md`.

- **Маршрутизация на шлюзе**: правило `ip rule` приоритета 100 `from 10.77.0.0/22 lookup 200|201` стоит РАНЬШЕ меток
  выходов (1000), поэтому российские адреса уходят в `eth0` минуя `gwx*`; всё, чего нет в таблице, падает в метки выходов, а
  без метки - в kill-switch (9000). Таблицы 200 и 201 используются по очереди: запасная заполняется, правило переключается.
- **`GatewayRuService`** (`ru.py`): `schedule_apply(server_id)` (быстрые проверки по БД: 404 нет сервера; 409 нет SSH-учётки,
  шлюза, активного списка или незавершённой такой же задачи; затем 202), `run_apply(job)` (воркер под `ServerLock` шлюза:
  эффективный список -> `apply_ru`; результат `{routes, table, prefixes}`), `ensure(provider, issues)` (сверка: есть активный
  список, а маршрутов на шлюзе не столько, сколько в эффективном списке, - применить; сбой - issue, не исключение),
  `health_check(provider)` (проверка `ru`) и `ensure_server(server_id)` (после установки шлюза, ошибки только в лог).
- **Задача `gateway_apply_ru`**: `server_id` = шлюз, без `params`; ставится API (`POST /api/v1/servers/{id}/gateway/ru/apply`,
  `servers:manage`, 202) и `GeoipService` после активации списка / изменения исключений (по одной на шлюз, без дублей).
  Занятый сервер - задача возвращается в очередь. Аудит: `gateway_ru_applied` (`routes`) и `gateway_ru_apply_failed`.
- **Сверка списка**: скрипт после успеха записывает в `ru.applied` отпечаток (первая строка `# sha256=<hex>` файла
  `ru.prefixes`, хэш префиксов ниже; ставит панель), `ru_status().digest` его читает. Список «применён», если совпали
  ОТПЕЧАТОК и число маршрутов (одного числа мало: другой список того же размера прошёл бы незамеченным).
- **Эффективный список шлюза** вычитает зарезервированные диапазоны и адреса самого шлюза и его выходов (/32): DIRECT-исключение,
  накрывающее адрес выхода или SSH-хоста, не ломает туннели и управление (сервис такое исключение и не принимает - 422).
- **Sync** шлюза (`servers/sync.py::_reconcile_ru`): отчёт `ru` = `{active_list, expected, routes, applied}`; нет активного
  списка - `{active_list: false}` и больше ничего. Расхождение отпечатка или числа маршрутов (таблица пуста после пересоздания
  контейнера, устарела или от другого списка) чинится применением списка. Сбой - issue "Failed to apply the Russian routes", sync
  не падает; испорченный список в БД - issue и `{error: true}` (текст без строк списка).
- **Health**: проверка `ru` добавляется, ТОЛЬКО когда есть активный список (иначе шлюз вечно был бы DEGRADED), «пройдена»,
  если применён именно эффективный список (отпечаток и число маршрутов); испорченный список - проверка не пройдена.
- **Установка**: `install_protocol` воркера после установки шлюза зовёт `ensure_server`: переустановленный шлюз получает
  маршруты обратно (если `ru.prefixes` сохранился на хосте, `start.sh` загрузит его сам); если активного списка ещё нет,
  ставится `GEOIP_UPDATE` (без дублей).
- **Известные ограничения**: страна по RIPE - страна регистрации блока (хостеры, CDN: российские сервисы за зарубежным CDN
  пойдут через выход; чинится `direct`-исключением); DNS клиентов идёт через выход; пока список применяется (около 4 секунд на
  8,6 тыс. маршрутов), новые соединения клиентов не страдают (в любой момент есть ровно одно рабочее правило 100), но
  уже установленные соединения к адресам, ушедшим из списка, продолжат идти с адреса шлюза до конца своей жизни; список
  применяется только к клиентам шлюза (обычный `amnezia_wg` не затронут); IPv6 не поддержан.
