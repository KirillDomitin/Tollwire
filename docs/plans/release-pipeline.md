# Проверяемые релизы и обновление панели

База: `80943d8db8bd9c77c52609f07f1ed7ab0c0bb955`.

Цель: собирать проверенный коммит один раз, проверять production-образы до публикации,
обновлять существующую панель готовым согласованным релизом без ручного составления команд.
Существующие локальные правки инструкций и HANDOFF.md не входят в реализацию.

## Решение

- Ручной workflow проверяет принадлежность SHA ветке master и успешный push CI этого SHA.
- app/web/bot собираются под linux/amd64, проходят smoke без production-секретов и публикуются
  в GHCR. Bundle фиксирует digest, SHA, Alembic heads и хеши Compose/nginx.
- GitHub не подключается к homelab. Оператор получает доверенный bundle и запускает deploy локально.
- Compose остаётся в корне; проект vpn-panel, тома, секреты и первая установка сохраняются.
- Оркестрация — стандартная библиотека Python 3 на сервере, shell-команды остаются точками входа.
- Lock → проверка/загрузка → остановка писателей → проверенный backup → миграция → запуск → smoke.
- Состояние и предыдущая конфигурация сохраняются атомарно в приватном .deploy/.
- Автовозврат только при прежней фактической схеме БД. Иначе maintenance и ручное recovery;
  автоматического restore/downgrade нет. Бот обновляется только если был запущен локально.

## Приёмка и ограничения

Не прошедший CI/подменённый manifest не приводит к остановке сервиса. Ошибка pull — до простоя.
Миграция запускается один раз после backup и остановки писателей; новый worker не исполняет
production-очередь в smoke. Существующие тома и настройки бота сохраняются. После ошибки схемы
никакая старая версия не стартует автоматически. Успешный релиз фиксируется после проверок.
Вывод проверок — итог и ошибки; подробности в логах, без секретов.

Без автоматического SSH, blue/green, переноса Compose и включения Caveman proxy.
Реальные серверы, push и коммиты — только по отдельному поручению.
