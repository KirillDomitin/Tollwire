# Выходной сервер выбранного устройства через бота

## Цель и принятый сценарий

Пункт 8 общего плана: пользователь выбирает своё VPN-устройство в Telegram-боте и меняет
его выходной сервер. Это назначение `credential → gateway exit`, а не перенос самого шлюза
или устройства на другой входной шлюз. Пользователь явно выбрал этот сценарий.

Конфиг, ключ, адрес устройства, подписка, занятые места лимита пяти устройств и маршруты других
устройств сохраняются. Можно выбирать только уже подключённые допустимые выходы своего шлюза;
создание выходов и администрирование серверов в задачу не входят.

База подготовки: `4900ba9da1ce89d41dba5a6649a3030a0a6154b5`.
Перед реализацией заново проверить HEAD и локальные изменения, сохранить чужую работу.
Этап 1 подготовлен 2026-11-16; реализация этапов 2–4 — после отдельных команд пользователя.
Коммит и деплой не разрешены.

## Существующий механизм и важные ограничения

- `GatewayFailoverService.move_client` (`src/modules/gateway/failover.py`) меняет назначение
  одного credential под `ServerLock` шлюза и поддерживает `pinned_exit_id`.
- Административный `PATCH /api/v1/servers/{server_id}/gateway/assignments/{credential_id}`
  требует `access:manage`. Бот не должен обходить авторизацию вызовом этого endpoint от имени админа.
- Карта применяется целиком: изменения БД → flush → применение → commit. Ошибка применения
  не должна превращаться в успешное изменение назначения в БД. Сохранять kill-switch.
- Существующий ручной административный перенос намеренно не ограничен `max_clients`.
  Пользовательскому самообслуживанию нельзя автоматически давать такое же исключение.
- Выход выбирается внутри конкретного шлюза. Пригодность определяется состоянием туннеля
  и существующими правилами назначения, а не общим `servers.health_status`.
- Старые соединения могут оставаться на предыдущем выходе до закрытия/переподключения:
  conntrack при переносе не очищается. Смена в БД не доказывает мгновенную смену IP всех соединений.

## Предлагаемая политика выбора

- Явный выбор сервера закрепляет устройство за ним (`pin=true`). Существующий failover продолжает
  работать: при отказе возможен временный перенос, затем возврат по штатным условиям/задержке.
- Показывать выбранный сервер и фактический текущий выход отдельно, если они различаются.
- Предусмотреть «Автоматический выбор»: снять закрепление, сохраняя существующую семантику сервиса.
  Снятие закрепления не обещает немедленную перебалансировку на другой сервер.
- Недоступный, удаляемый или заполненный выход не предлагается как допустимая цель.
  Повторная проверка обязательна в момент применения; список мог устареть.
- Повторный выбор уже применённого сервера безопасен и не расходует дополнительную ёмкость.

Эта политика является конкретным предложением ТЗ. На этапе 1 architect проверяет совместимость
с текущим failover/ёмкостью и фиксирует окончательный контракт. Только фактическую архитектурную
развилку передавать пользователю, не переспрашивать уже выбранный сценарий одного устройства.

#### Предлагаемый контракт (до реализации)

База URL: `/api/v1/bot/users/by-telegram/{telegram_id}/devices/{credential_id}`.

- `GET /exit-options`: `credential_id`, `device_name`, `current_exit: {id,name}|null`,
  `pinned_exit: {id,name}|null`, `mode: automatic|pinned`, `revision: UUID|null`,
  `exits: [{id,name,selectable,reason: null|unavailable|full}]`.
  `revision=null` означает отсутствие назначения, а не отсутствие проверки.
- `PATCH /exit`: `{exit_id: UUID|null, expected_revision: UUID|null}`.
  UUID цели означает перенос с закреплением; `null` — только unpin, фактический выход сохраняется.
  Ответ 200 содержит актуальный DTO чтения. При отсутствии назначения unpin отклоняется как `not_ready`.
- Одинаковый 404 для отсутствующего пользователя и чужого/неподходящего credential.
  409 с фиксированной `reason`: `no_access`, `not_ready`, `exit_unavailable`, `exit_full`,
  `gateway_busy`, `stale_confirmation`. Чужой/исчезнувший выход — `exit_unavailable`, без его данных.
  401/422/429 — действующие правила; ошибка применения — безопасный 502.
- Только действующий ключ бота, без `access:manage`. Как в существующем API, ключ бота доверенный
  относительно Telegram ID; бот берёт ID исключительно из `from_user` и принимает сценарий в личном чате.
  Bot API сам не может доказать тип Telegram-чата, поэтому эта проверка обязательна в боте.
- DTO/логи/ошибки не содержат адресов, конфигов, ключей и SSH-данных.

#### Домен, авторизация и гонки

Переиспользовать `GatewayFailoverService.move_client` с явно ограниченным пользовательским режимом.
Административный контракт и его обход `max_clients` по умолчанию сохранить. Проверки вне доменного
переноса не заменяют повторную авторизацию внутри него.

1. Предварительный `BotDeviceService.owned` определяет шлюз и отсекает чужой credential.
2. Взять `ServerLock` шлюза; для переноса выполнить существующие `_provider`/`_ready`.
3. **После `_ready`** заново взять DB locks и свежие строки: protocol шлюза → subscription → grant →
   credential → assignment/целевой выход. `_ready` может commit при recreate; ранние row locks через
   него не сохраняются. Перед реализацией сверить этот порядок с путями отзыва на отсутствие дедлоков.
4. Повторить владельца, принадлежность протоколу, ACTIVE/non-revoked credential, действующий доступ
   (`inactive_reason`), revision, принадлежность цели и её пригодность/ёмкость.
5. Для нового назначения: ACTIVE, `consecutive_failures == 0`, health вне `UNUSABLE_HEALTH`,
   проверка туннеля существующим механизмом кандидатов. Ошибка проверки цели означает отказ.
   `counts` и `assigned < max_clients` проверяются под ServerLock; текущий клиент не считается новым.
6. Сохранить порядок: готовность → изменения БД → flush → полная карта → commit.
   Ошибка применения — rollback и отсутствие успешного ответа. Unpin без переноса карту не применяет.

`ServerLock` сериализует failover и worker удаления, но HTTP `schedule_remove` меняет DRAINING
под `lock_gateway`, поэтому нужен и protocol row lock. Credential row lock сериализует
`schedule_revoke`; subscription/grant locks — изменение доступа до commit операции.
Основа: `gateway/failover.py:move_client`, `assignment.py:_ready/_candidates`,
`repository.py:lock_gateway/counts`, `service.py:schedule_remove`, `access/service.py:schedule_revoke`.

Выбор закрепляет устройство, штатный failover и возврат сохраняются. Автоматический режим снимает
закрепление без немедленной перебалансировки. Фактический и закреплённый сервер показываются отдельно.
Conntrack не очищать; после успеха можно предложить переподключить VPN.

#### Решения до кода — согласованы пользователем

Рекомендация: **синхронный перенос**, как административный. Нового JobType не требуется.
Таймаут PanelClient может наступить после фактического успеха: ниже описано безопасное восстановление.
ServerLock ожидает захват 5 с, TTL равен `stale_job_timeout_seconds`, продления нет; не расширять
общий механизм блокировки в этой фиче. Это существующий предел, который нужно учитывать в проверках.

Рекомендация: **миграция `GatewayAssignment.revision: UUID`** с новой версией при каждом изменении
фактического выхода или pin во всех доменных путях, включая admin/failover/возврат/drain.
Новая строка получает новую UUID, чтобы удаление/повторное создание не возвращало старую версию.
No-op версию не меняет. CAS `expected_revision` проверяется под блокировкой; несовпадение —
`stale_confirmation` без изменения назначения. Отсутствующая строка сравнивается с `null`.

Обоснование: `assigned_at` меняется при переносе, но не при pin/unpin. Снимок текущих полей пропускает
ABA: pin A → unpin → pin A. SQLite/Redis-токен без миграции потребует инвалидации во всех доменных
путях и согласованности с commit БД; это сложнее и не рекомендуется. Миграция добавляет обязательные
upgrade/downgrade и полный прогон по правилам репозитория.

Отдельный durable receipt не вводить. После потерянного ответа повтор с прежней revision безопасно
получает stale; бот делает GET и сообщает подтверждённое актуальное состояние. Автоматически повторять
перенос с новой revision нельзя. Это не обещает исторического exactly-once ответа.
