# Ручное обновление контейнеров протоколов

## Задача и решение

Добавить ручное обновление установленных панелью AmneziaWG и Amnezia Gateway до последнего образа доверенного upstream. Пользователь выбрал вариант 2: запуск из интерфейса, без автоматического расписания.

Источник обновления — фиксированный репозиторий `amneziavpn/amneziawg-go`, канал `latest`; пользователь не задаёт образ или команды. После загрузки фиксируется immutable digest, именно он используется для запуска. Закреплённый образ обычной установки сохраняется. Внешние APP_AWG/APP_AWG2 не обновляются.

Операция выполняется фоновой задачей под ServerLock. До остановки скачивается образ и проверяется принадлежность контейнера. Совпадающий образ не вызывает перезапуск. Сохраняются конфиги, ключи, peer'ы, порт и настройки шлюза. Старый контейнер и image сохраняются для отката до успешной проверки нового. При обрыве SSH/воркера повтор операции должен восстановить незавершённую замену. Uninstall/install для обновления не используются.

## Контракт реализации

- `POST /api/v1/servers/{server_id}/protocol/update` → 202 JobRead; выбор `type` в теле или query как у установки (по умолчанию AWG), несовпадение → 422. Чужие APP-протоколы → 422, отсутствующий протокол → 404, отсутствие SSH-учётки или незавершённая задача обновления сервера → 409.
- `JobType.UPDATE_PROTOCOL = "update_protocol"`; `params.protocol_type` всегда задан явно. Воркер повторно проверяет протокол под ServerLock.
- `VPNProvider.update()` по умолчанию запрещён через UnsupportedOperationError. Результат `ProtocolUpdateResult`: changed, previous_image_id, target_image_id, target_digest, rollback (`not_needed/succeeded/failed`), recovered (по умолчанию false). Job.result дополняется protocol_type. Ошибка обновления сохраняет несекретный job_result; неизвестные image-поля допустимо оставить null.
- `AMNEZIAWG_UPDATE_IMAGE = "amneziavpn/amneziawg-go:latest"`; RepoDigest допускается только для этого репозитория с sha256 из 64 lowercase hex. Image ID сравниваются отдельно от manifest digest. Latest означает последнюю публикацию этого канала, а не обязательно последний стабильный GitHub release.
- Перед заменой сохраняется приватная копия всего bind mount и атомарный журнал `.container-update.json` без секретов; backup-контейнер `<name>-update-backup` сохраняется до успешной проверки. Откат восстанавливает также конфигурационные файлы. Recovery проверяет ID объектов, восстанавливает прежний контейнер при повторном вызове, не трогает неизвестные объекты; без нового вызова автономное восстановление не обещается.
- Проверка готовности: интерфейс, прежние порт и peers, NAT; у шлюза также kill-switch, выходы, назначения и российские маршруты. Свежий handshake не обязателен.
- Аудит `protocol_update_started/completed/failed`: тип протокола, image ID/digest и changed/rollback/recovered, без секретов.
- UI: действие для своего протокола с servers:manage, подтверждение краткого разрыва, polling задачи и итог с состоянием отката.

## Проверки

Сохранение ключей/клиентов/порта, отсутствие перезапуска при совпадении image, запрет чужих контейнеров и внешних протоколов, pull до остановки, ошибки запуска/проверки/отката, восстановление после обрыва, правила шлюза, RBAC, аудит без секретов, upgrade/downgrade миграции, действие и права в UI.

## Риски

Краткий разрыв VPN и возможный failover шлюза. Последняя upstream-версия может быть несовместима с текущим форматом; автоматические миграции конфигурации не входят в задачу. Доверие к latest ограничено фиксированным репозиторием, но digest фиксирует скачанный образ, а не гарантирует его безопасность. Ошибка registry не должна останавливать работающий VPN. Откат должен учитывать изменение конфигурации новым контейнером и внешние изменения Docker.

### Расширение запроса: обнаружение обновлений

Подтверждённое требование: проверять доступность нового образа, показывать сообщение в интерфейсе конкретного сервера/протокола. Само обновление остаётся ручным. Пользователь назначил проверку ежедневно в 03:00; часовой пояс Europe/Moscow (контекст пользователя), независимо от timezone процесса. Интервал в 86400 секунд от старта не заменяет календарный график. Использовать существующий scheduler и Redis-дедупликацию по календарной дате; несколько воркеров не должны дублировать ежедневный запуск. Поведение пропуска времени при остановленном воркере: один догоняющий запуск после 03:00 за текущую дату, без воспроизведения прошлых дней.

- Добавить `VPNProvider.image_info()`: read-only inspect фактического image ID контейнера и платформы установленного образа. Проверка никогда не вызывает pull/stop/run и не меняет health_status.
- Registry V2: читать metadata только фиксированного upstream, общий Redis-кеш для серверов, ограниченные timeout/размер ответа и доверенные registry/auth hosts. Для multiarch выбрать manifest платформы установленного образа и сравнить его config.digest с локальным image ID; digest index не сравнивать с child/image ID. Неоднозначная платформа → unknown.
- Scheduler: отдельное ежедневное правило 03:00 Europe/Moscow, сбор по образцу MetricsCollector с ограниченной параллельностью и изоляцией ошибок серверов. Никогда не планировать UPDATE_PROTOCOL автоматически.
- Redis: наблюдения по protocol_id, статусы current/available/unknown/unsupported, checked_at/last_attempt_at, stale и безопасный reason. Последний успех хранить семь дней. Для ежедневного расписания считать результат устаревшим после 26 часов либо сразу после неуспешной попытки; прошлое успешное наблюдение сохранять с датой. При пустом кеше показывать unknown. Остатки кеша удалённых протоколов не возвращать.
- GET `/api/v1/servers/{id}/protocol/updates` (servers:read) отдаёт только кеш без сети; POST `/api/v1/servers/{id}/protocol/updates/check` (servers:check) → 202 CHECK_PROTOCOL_UPDATES для обоих собственных протоколов сервера, с дедупликацией. Проверку не публиковать как достоверную в промежуточной фазе обновления контейнера.
- UI: сообщение «Доступно обновление» у конкретного протокола, актуальное/неизвестное состояние и время проверки; устаревшие сведения обозначать явно. «Проверить сейчас» с servers:check; ручное обновление с servers:manage. После обновления повторить проверку/инвалидировать кеш.
- Расширить enum-миграцию CHECK_PROTOCOL_UPDATES; дополнительных таблиц не требуется.
- Расширить красные тесты: календарный запуск и дедуп по дате, догоняющий запуск, multiarch без ложных обновлений, read-only поведение, кеш/offline/stale/429, API/RBAC и UI-сообщение у конкретного протокола.

Тестовые контракты расширения: `ProviderImageInfo`/`VPNProvider.image_info()`; `infrastructure/vpn/registry.py` — `RegistryImageInfo(image_id, digest)`, `AmneziaImageRegistry.latest_for(image)`, выбор manifest по платформе; `modules/servers/protocol_updates.py` — `ProtocolUpdateCheckService(session, registry=None, clock=None).check/get_cached`, результат `{protocols: [...]}`; scheduler `check_protocol_updates_daily(now=None)` вызывает `collect_protocol_updates()` и проверяется существующим Rule раз в 60 секунд. Дневной claim фиксирует попытку скана, индивидуальные ошибки серверов отражаются в кеше; при общем инфраструктурном сбое claim освобождается для повторной попытки.
