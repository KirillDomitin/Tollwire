# Устройства шлюза

## Лимит и модель

Владелец — VPNUser. Один VPNCredential соответствует одному peer и отдельному конфигу.
Лимит — пять неочищенных gateway-credentials суммарно по всем шлюзам и подпискам пользователя.
Это не распознавание физических устройств: скопированный конфиг остаётся одним credential.
Существующие превышения не удаляются; новая выдача запрещена до освобождения места.
Прямой AWG и импортированные APP-протоколы сохраняют политику одного живого credential на grant.

Новые поля VPNCredential: `state`, `is_gateway`, `device_name` (до 100 символов, только подпись),
`peer_name`, `request_id` (nullable UUID, UNIQUE). Незавершённая запись может не иметь адреса,
публичного ключа и конфига. Для ACTIVE обязательны адрес/ключ и, у ISSUED, зашифрованный конфиг.
У IMPORTED приватного ключа нет, поэтому отсутствие конфига допустимо и у готового клиента.

| Состояние | Действие | Место |
|---|---|---|
| RESERVED | Резервация и задача записаны до SSH | Занято |
| PROVISIONING | Намерение выдачи закоммичено до изменяющего SSH | Занято |
| ACTIVE | Конфиг сохранён; назначение выхода может повторяться отдельно | Занято |
| REVOKING | Отзыв принят, очистка ещё не подтверждена | Занято |
| REVOKED | Очистка подтверждена, заполнен revoked_at | Свободно |

Счётчик использует `revoked_at IS NULL`, включая истёкший доступ, failed Job и незавершённый отзыв.
Показ, скачивание и повторная ссылка не резервируют место.

## Резервация, задачи и SSH

`stage_issue` блокирует VPNUser, перечитывает доступ и считает gateway-credentials по всем шлюзам.
Резервация и задача создаются одной транзакцией; `schedule_issue` коммитит и ставит задачу в Redis.
Регистрация бота использует тот же механизм вместе со своими записями. Сбой enqueue после commit
не освобождает место: существующий requeue доставляет задачу позже.

`request_id` на повторе возвращает ту же операцию после проверки гранта. Чужой request/credential
не раскрывает данные. Новая gateway-выдача использует CREATE_DEVICE, отзыв — REVOKE_DEVICE.
У non-gateway сохраняются CREATE_USER/REVOKE_ACCESS, но новые задачи тоже несут
`params.credential_id`. Worker проверяет соответствие credential, grant и server и работает адресно.
Только действительно старые задачи без target сохраняют grant-семантику; старый массовый отзыв
снимает все credentials гранта.

Новые gateway peer-имена — `dev-` + base32(UUID.bytes) в нижнем регистре без padding:
30 безопасных ASCII-символов, все 128 бит UUID сохранены. Подпись устройства не попадает в SSH.
Legacy `peer_name=NULL` использует прежнее `grant-<12 hex>`; прочие протоколы сохраняют grant-имя.

Перед SSH credential перечитывается FOR UPDATE; PROVISIONING фиксируется отдельным commit.
Повтор ACTIVE возвращает тот же ключ и повторяет назначение выхода. Повтор PROVISIONING сначала
вызывает provider.ensure_client_removed по точному имени/сохранённому ключу; лишь после подтверждения
очистки создаёт peer для того же credential. Потерянный SSH-ответ или commit не делает место свободным.
После SSH доступ и credential проверяются повторно под блокировками; отзыв нельзя затереть ACTIVE.

Индивидуальный отзыв не меняет grant и не затрагивает соседние устройства. Отзыв grant/подписки и
истечение охватывают все credentials и резервации. Место освобождается после подтверждённой уборки;
ошибка detach не возвращает peer, карту выходов исправляет sync.

Отсутствия peer в файле недостаточно: SSH мог сохранить файл и потерять ответ до применения к
интерфейсу. Для собственного AWG/шлюза ensure_client_removed повторно применяет сохранённый конфиг,
даже если целевого peer уже нет в файле, затем сверяет runtime-ключи через client_stats с оставшимися
peer-файла. Несовпадение или недоступность runtime не подтверждает уборку, слот сохраняется.
APP использует прежний адресный revoke по ключу. Отзыв, cleanup pending и stale-sync вызывают
этот провайдерный контракт до закрытия credential.

## Sync и готовность

Sync восстанавливает только ACTIVE с живым доступом, используя сохранённое peer-имя либо legacy-имя.
RESERVED с живым доступом остаётся в очереди; PROVISIONING/REVOKING и неактивные резервации
очищаются под ServerLock и закрываются только после подтверждения. Retry закрытого target не
создаёт замену. Сироты распознаются по прежнему grant-префиксу и строгому новому dev-имени.
Назначения выходов и метрики используют только готовые credentials с ключом/адресом.

## API и интерфейсы

Административные GET/POST `/api/v1/vpn-users/{user_id}/gateway-devices` требуют `access:read` /
`access:manage`. GET возвращает `{limit:5, occupied, devices, gateways}`. У устройства — metadata
VPNCredentialRead, в том числе `state`, `device_name`, `has_config`, `is_gateway`; без конфига/ключей.
У доступного шлюза — `{grant_id, protocol_id, server_id, server_name}`. Записи устройств сохраняются
в списке до уборки, даже если их grant уже отсутствует в доступных шлюзах.

POST принимает `{grant_id, device_name?, request_id}`; grant и UUID запроса обязательны, подпись
1–100 символов. Ответ 202 JobRead; превышение — 409 с `reason=device_limit`, чужой/неподходящий
grant — 404. Существующий POST `/access/{grant_id}/credentials` принимает необязательные
`device_name` и `request_id`; прежние config/revoke endpoints сохранены.

В панели — общий список, занято/5, явный шлюз при нескольких вариантах, адресный конфиг/QR/ссылка
и отзыв. Незавершённые записи опрашиваются после перезагрузки. ACTIVE без действующего gateway
показывается ожидающим удаления, конфиг не открывается. Статистика и выход относятся к credential_id.

Bot API повторяет операции по Telegram-пользователю с проверкой владельца на каждом запросе:
[контракт](../bot/api.md). `/devices` — отдельное меню шлюзов, подпись ограничена 64 символами.
`/config` сохраняет прежний выбор одиночной ссылки для совместимости со смешанными протоколами.
Адресная ссылка меняет только ссылку выбранного устройства. Pending → not_ready, отзыв/нет доступа →
no_access; неправильный/чужой ID → 404. Ни списки, ни аудит не содержат конфигов/секретных ключей/токенов.

## Миграция и откат

`g8c2e4a61d90` после `a9d1e6c42b70` сохраняет старые ключи/конфиги, выставляет ACTIVE/REVOKED
по revoked_at и определяет is_gateway через протокол. Уникальность живого credential на grant
остаётся только для `NOT is_gateway`; добавляются lifecycle-поля и ограничения готовых записей.

Downgrade сначала отказывает при нескольких живых credentials на grant, незавершённом lifecycle,
NULL адресе/ключе или отсутствии ISSUED-конфига. Проверяются все исторические строки: отозванная
резервация без прежних обязательных данных также несовместима. Дополнительные устройства нельзя
удалять либо заполнять выдуманными данными ради отката. Нужна совместимая миграционная стратегия
оператора; один только успешный отзыв не гарантирует совместимость старой схемы.

Также запрещён откат при PENDING/RUNNING новых device-задач и адресных CREATE_USER/REVOKE_ACCESS.
Завершённые CREATE_DEVICE/REVOKE_DEVICE переводятся в понятные старому ORM CREATE_USER/REVOKE_ACCESS;
строки истории сохраняются, неиспользуемые PostgreSQL enum labels остаются. Только после проверок
возвращаются старые ограничения и удаляются новые колонки.

API и worker обновляются согласованно с остановкой старых процессов. Смешение версий запрещено:
старый worker не знает новые JobType и игнорирует credential-target у прежних типов.
