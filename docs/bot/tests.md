# modules/bot — перечень тестов

Слои и правила тестов — в `tests/CLAUDE.md`. Здесь — что проверяет каждый файл бота.

## Общее

- `tests/bot_support.py` — сцены и обёртки над сервисами модуля, константы контракта (префиксы, причины отказа,
  статусы). Если сигнатура сервиса меняется, правится этот файл, а не десятки тестов.

## unit

- `unit/test_bot.py` — схемы запросов: имя (1–64, без управляющих и невидимых символов), `telegram_username`,
  `telegram_id` (BIGINT), почта, код приглашения (≤64), `heartbeat` (имя бота, версия), срок приглашения (1–3650
  дней), обязательность протокола и срока; генерируемый код укладывается в `start`; `invite_status` (valid, срок
  до момента включительно, used остаётся used после срока, revoked); `InviteFree` всегда `PAID`.
- `unit/test_bot_secrets.py` — `hash_token` (SHA-256 hex, стабильность, отличие по значению), `generate_token`
  (длина, уникальность, URL-безопасность), в хеше нет открытого значения.
- `unit/test_bot_redaction.py` — маскировка `twb_…`, значения `X-Bot-Key` и поля `code` в логах; имя поля остаётся;
  JSON-строка лога остаётся валидным JSON; текст без секретов не меняется.

## services (Postgres и Redis)

- `services/test_bot_keys_invites.py` — ключ хранится только хешем, префикс — 8 символов, каждый ключ уникален и
  длинный; создание и отзыв аудируются без ключа; повторный отзыв не меняет время и не пишет второе событие;
  приглашение хранится хешем, протокол и срок сохраняются; приглашение неизвестного протокола и уже истёкшее
  отвергаются; `check` не меняет данные и не раскрывает подробности; отзыв идемпотентен; ссылка `t.me` указывает на
  имя из heartbeat и экранирует код; удаление протокола оставляет приглашение без протокола.
- `services/test_bot_registration.py` — регистрация: пользователь с полями Telegram, подписка на срок приглашения с
  текущего момента, грант на протокол приглашения, одна задача `CREATE_USER` без секретов; аудит без кода, почты и
  `telegram_id`; повтор тем же `telegram_id` возвращает ту же регистрацию без новых объектов (в том числе после
  выдачи и после `failed`); чужой `telegram_id` → `invite_used`; `email_taken` (без учёта регистра) и
  `telegram_taken` ничего не создают; неизвестное, истёкшее, отозванное приглашение и удалённый протокол — отказ без
  объектов; неоплаченная регистрация (заглушка `PENDING`) ждёт без доступа и держит приглашение; гонки (два
  `telegram_id` на одно приглашение, две почты с разным регистром) — проходит один; хук (SUCCESS → active, FAILED →
  failed с сохранением пользователя и гранта, текст ошибки SSH с секретом маскируется, чужая задача не трогает
  регистрации, падение хука откатывает итог задачи); правило `stale_jobs` закрывает регистрацию без хука; `reconcile`
  (failed, active при живом клиенте, в полёте не трогает, идемпотентен, не понижает failed без изменений); `retry`
  (выдача, тот же пользователь и грант, второй retry в `provisioning` и retry active → 409, отозванный грант → 409,
  неизвестная → 404, повторный сбой → снова failed; устаревшая упавшая задача не роняет регистрацию, уже
  повторённую админом).
- `services/test_migrations.py` — миграция `a7d3e9b15c28`: таблицы и колонки, `telegram_id` уникален, но у многих
  пользователей может быть NULL; уникальность ключа и кода; CHECK дней; ограничения по приглашению, открытой
  регистрации и гранту; удаление протокола, админа, пользователя или ключа оставляет строки (SET NULL); downgrade
  удаляет таблицы и колонки, пользователи остаются; цикл upgrade/downgrade идемпотентен.

## integration (через HTTP)

- `integration/test_bot_auth.py` — 401 на каждом маршруте без ключа, с пустым, неверным, почти совпадающим и
  отозванным ключом; JWT админа не открывает Bot API, ключ бота не открывает админский API (ни как заголовок, ни как
  bearer); отказы одинаковые; отзыв в панели останавливает бота сразу, другой ключ работает; heartbeat обновляет
  время, имя и версию, не трогает чужой ключ, отклонённый ключ следов не оставляет; неверный heartbeat — 422; лимиты
  по ключу и регистрациям — 429 с `Retry-After`; ограниченный ключ остаётся ключом, панель работает.
- `integration/test_bot_flow.py` — сквозной сценарий: ключ → приглашение → `POST /registrations` → `drain(worker)` на
  фейковом сервере AmneziaWG → `active` → `users/by-telegram`; клиент виден в панели как обычный; статус неизвестного
  telegram и регистрации — 404; проверка кода не раскрывает детали; повтор регистрации; занятые почта и Telegram —
  409 без эха; истёкшее и отозванное приглашение; неверный ввод — 422 без объектов; сбой выдачи → retry → `active`;
  второй retry и retry active — 409; retry после отзыва доступа — 409; приглашение на шлюз выдаёт клиента шлюза с
  выходом; списки ключей и приглашений без секретов; права: viewer читает и не пишет, operator управляет
  приглашениями, но не ключами, ключ выпускает только superadmin, открытый ключ один раз в ответе; секреты не
  попадают в аудит и `Job.params`.
- `integration/test_rbac.py` — `/api/v1/bot/*` исключён из общей матрицы; на каждом маршруте Bot API ровно одна
  метка `bot_key_required` и нет прав админа; ни один маршрут админского API не принимает ключ бота; права
  `/api/v1/bot-admin/*` (чтение — `bot:read`, ключи — `bot:keys`, остальное записи — `bot:manage`); матрица ролей
  (viewer не пишет); `POST /api/v1/bot-admin/keys` — `bot:keys` в списке критичных маршрутов.

## Бот в репозитории: корневой `tests/`

Тесты самого бота (`bot/tests`) — в `docs/bot-service/tests.md`. Здесь — то, что стыкует бот с панелью и установкой.
Общие сцены: `tests/bot_client_support.py` (настоящий `PanelClient` без aiogram), `tests/bot_cli_support.py` (`Console`
и отказы скриптов), заглушки установщика — `tests/unit/install_support.py`.

### unit

- `unit/test_bot_isolation.py` — обход AST всех `bot/**/*.py` (код и тесты): нет импортов `core`, `modules`,
  `infrastructure`, `scripts`, `main`, `worker`, `src`; `PanelClient` требует только httpx, certifi и stdlib; в
  зависимостях `bot/pyproject.toml` нет стека панели; `bot/` содержит свой Dockerfile, compose, `.env.example`,
  установщик; корневой `.dockerignore` исключает `bot`.
- `unit/test_bot_review_fixes.py` — исправления по ревью: исполняемые скрипты с режимом `+x` в git; секреты бота и
  временные файлы установщиков не коммитятся, `bot/.env.example` в git; Compose ниже 2.24 останавливает установщик и
  все команды `./panel`, нечитаемая версия старой не считается; адрес репозитория для `git clone` без порта ssh и
  учётных данных, адрес с метасимволами не печатается в команду; `curl -q` не читает `~/.curlrc`.
- `unit/test_install_bot.py` — `install.sh --bot local` (`install_support.py`: `FakeDocker`, `FakeCurl`): токен и ключ не
  попадают в вывод, `ps` (аргументы) и `.env.prod` (только `COMPOSE_PROFILES=bot`, остальные строки байт в байт);
  `.env.bot` 0600; `getMe` не прошёл → предупреждение и выбор; повторный запуск и `update` не спрашивают; вопрос
  «1/2/3» — в псевдотерминале (POSIX).
- `unit/test_install_bot_remote.py` — `install.sh --bot remote` и `bot/install-bot.sh` на втором сервере: ключ виден один
  раз и только в терминале, в команду для второго сервера не вставляется; отпечаток сверяется до записи `bot/.env`;
  TLS-сервер в процессе теста с сертификатом той же командой openssl; `--reconfigure` меняет только ключ; 401 и сбой
  сети выводятся разными сообщениями.
- `unit/test_panel_bot.py` — `./panel bot enable|disable|key|key --remote|revoke|status|invite`: `disable` убирает
  профиль и оставляет ключ действующим; `key` записывает новый ключ, перезапускает бота и только потом отзывает старый;
  если новый не вышел на связь, старый не отзывается.
- `unit/test_ship_images.py` — `ship-images.sh` собирает третий образ `vpn-panel-bot`, если есть `bot/`, и тегирует его на
  сервере.

### integration

- `integration/test_bot_client_contract.py` — настоящий `PanelClient` против настоящего API (`ASGITransport`, воркер,
  фейковый SSH): каждый метод; каждый `reason` 409; 422 с именем поля; 401 для неверного и отозванного ключа (без
  повторов); 429 по лимиту регистраций; ключ не попадает в аудит после целого диалога.
- `integration/test_bot_key_cli.py` — `scripts.bot_key` (`create`, `revoke`, `list`, `seen`): ключ один раз и только в
  терминале или с `--raw`; отказ вне терминала до выпуска; в БД только хеш; аудит `source: cli` без ключа; `revoke` и
  `seen` читают ключ из stdin.
- `integration/test_bot_invite_cli.py` — `scripts.bot_invite` (`protocols`, `create`): ссылка или код один раз; срок
  `7d` или `12h`; отказ вне терминала до создания; в аудите `source: cli` без кода и ссылки; приглашение неотличимо от
  созданного через API.
